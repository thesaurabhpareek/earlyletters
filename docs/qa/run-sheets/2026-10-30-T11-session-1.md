## Staging SQL for block 8 (founder, SQL editor on `scribe-staging` only)

The SQL editor runs as the database owner and ignores access rules, so every statement names Drill E's id (Authentication > Users, found by Mailbox 7) and checks the row count. Paste the id only into the editor; it never goes into evidence, an issue or a chat. Never edit a statement to a broader `where`, and never run one on production.

**T11-A. After the confirm, read only.** It must return exactly one row. If it returns none or more than one, stop: change nothing, cancel nothing by SQL, and tell S14 and S19.
```sql
select id, status, scheduled_for
  from public.deletion_requests
 where profile_id = '<Drill E user id>'
   and kind = 'account'
   and status = 'scheduled';
```

**T11-B. After Cancel deletion, read only.** One row, `status` = `cancelled`.
```sql
select status, cancelled_at is not null as cancelled
  from public.deletion_requests
 where profile_id = '<Drill E user id>'
   and kind = 'account'
 order by requested_at desc
 limit 1;
```

**T11-C. Only for a run to completion on Drill E in W5 or W6**, after a new request in the app and after T11-A returns exactly one row for it. It changes exactly one row or nothing: if the count is not 1 it raises an error and the change is undone. If the editor shows the error, stop.
```sql
do $$
declare n integer;
begin
  update public.deletion_requests
     set scheduled_for = now()
   where id = '<the id from T11-A>'
     and profile_id = '<Drill E user id>'
     and kind = 'account'
     and status = 'scheduled';
  get diagnostics n = row_count;
  if n <> 1 then
    raise exception 'stop: % rows matched, expected exactly 1; nothing was changed', n;
  end if;
end $$;
```
Then the purge worker and `scripts/ops/verify-deletion.ts`, as AL-07.7 and AL-07.8 describe (G3 for C1).
