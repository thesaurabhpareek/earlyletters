# Security risk register

Status: **DRAFT for the exec team's CISO read. Not approved. No risk here is accepted.** Written 27 Nov 2026 for BL-241 (LEGAL-REQ-028). Companion: [WISP.md](WISP.md). Nothing here was run against a hosted project, a vendor console or a phone.

Every risk comes from a file in this repository, named in its row. Where a fact may have changed since that file was written, the row says the file's date. The scores are the drafter's, for the CISO read to change.

How to read a row:
- **Likelihood (L)** and **Impact (I)**, 1 (low) to 5 (high). Score = L x I. Impact 5 means L4 content (letters, recordings, the child's details) reaches someone it should not, or a credential that opens them leaks.
- **Likelihood anchors** (proposed, for the CISO read to change), each over the 12 months to the next annual review:
  - 1: not expected in 12 months; it needs a precondition that does not exist today, or several controls failing at once.
  - 2: could happen in 12 months; a path exists, but it needs a deliberate actor or one specific mistake, and none has been seen.
  - 3: plausible in 12 months; the path is live and rests on one control that is procedure or has not been read back.
  - 4: expected in 12 months; the gap is open now and ordinary work will meet it.
  - 5: happening now, or expected within the quarter.
- **Controls** say whether each is a test, a setting, or procedure (see WISP section 3). Procedure is not counted as a control.
- **Owner** is a role. **Next** is the next action and its backlog id or founder queue row, if one exists. "No BL id found" means none was found in `docs/BACKLOG.md` for this draft.
- **Review by**: 2027-02-27 for every row, proposed. That is quarterly, the cadence [SECURITY.md](SECURITY.md) section 2.6 sets for the other reviews. The CISO read sets the real dates.
- Accepting a residual risk is an exec-review decision (CR-176; `.claude/skills/early-letters-ciso/SKILL.md` section 4). Until one is recorded, every row is open.

### R-23 The pack and config signing key is copied or misused
- **What:** one Ed25519 key signs the pack manifest, the remote config and the content bundle: both trusted keys, `el-2026-11` and the cold backup `el-2026-11-backup`, may sign all three kinds (`packages/api/src/keys.ts`). The remote config carries the kill switches and `forceReauthEpoch` (`packages/api/src/remote-config.ts`; R-10, R-11). Someone with the key and a way to serve a document could turn off a kill switch set during an incident, raise `forceReauthEpoch` and sign every phone out, change the prompts, tips and announcements the app shows (ADR 0016 section 5.1), or publish a pack manifest the app trusts. ADR 0016 section 4.2 says the app refuses a document whose version is lower than the last one it accepted; the drafter's reading, not tested, is that a forged document with a high version would also hold off later genuine ones until phones have a release that drops the key. Serving needs a second step: an upload to the pack host with the R2 upload key (PACKS_HOSTING step 7), or a change to the signed documents the `config` function serves (`supabase/functions/config/published.ts`, generated by `scripts/packs/publish.ts`), merged and deployed (R-21). SECRETS.md says of the R2 key that "the signature still stops the app trusting a forged one", which stops holding once the signing key is out too.
  - Where the private key lives: [PACKS_HOSTING.md](PACKS_HOSTING.md) "Signing key custody and rotation" puts the primary in the password manager and in a key file on the publishing computer, outside every git checkout, and the backup in its own password manager entry and an offline copy. The `EL_SIGNING_KEY` row of [SECRETS.md](SECRETS.md) says "password manager and one offline copy", which leaves out the key file, and its "If it leaks" names packs only; `keys.ts` says "the password manager and the signing shell's environment". So the primary sits on the computer of R-20, in the same folder as the R2 upload key's file (PACKS_HOSTING steps 1 and 5). The CISO skill section 9a says no CI job reads the signing secrets (D-115 item 2).
  - Rotation is documented (PACKS_HOSTING; the `keys.ts` header; ADR 0016 section 4.2): add a key, ship an app release, sign with it, drop the old key in a later release. A leak is answered by signing with the backup and removing the leaked key in the next release, and "until phones have that release, documents signed with the leaked key are still accepted". The signing key is not in the rotation calendar of [SECURITY.md](SECURITY.md) section 2.6, no rotation date is recorded after the first ceremony of 1 Nov 2026 (`keys.ts`), and the leaked-key steps have not been drilled.
- **Why impact 4 and likelihood 2:** the key opens no letter or recording, so impact is not 5; but it takes away the incident levers (kill switches and the forced sign-out) and puts words in front of every family, and only an app release revokes it. Likelihood 2: it is used rarely, on one computer and never in CI, but it sits in a file on that computer, and the second step it needs is either the R2 key, in a file next to it, or the merge path of R-21.
- **Source:** `packages/api/src/keys.ts`; `packages/api/src/remote-config.ts`; [ADR 0016](../adr/0016-lean-app-and-server-driven-content.md) sections 4.2 and 5.1; [PACKS_HOSTING.md](PACKS_HOSTING.md) steps 1, 5, 7 and 8 and "Signing key custody and rotation"; [SECRETS.md](SECRETS.md) rows `EL_SIGNING_KEY` and `PACKS_S3_SECRET_ACCESS_KEY`; [SECURITY.md](SECURITY.md) section 2.6; R-11; WISP section 4; `.claude/skills/early-letters-ciso/SKILL.md` section 9a.
