## Context

Photo with a letter keeps one stripped picture per letter on the phone only. Sync keeps `entries.photo_path` null (NS-01-R15). The mobile engineer is blocked on three decisions (the phone table, the export bump, the server write-deny test) and Find and the sealed letter need answers that touch the same tables.

Facts that shape the answer [R]:

1. The server already has an `entry-photos` bucket with author insert, update and delete policies, and an `entries.photo_path` column that a client may set to a valid path of its own entry. Nothing in the server today refuses a photo upload. "Photos never leave the phone" is therefore a promise kept only by the app. That is the gap BL-870 closes.
2. Erase everything (`wipe.removeEverything`) deletes every row of every table named in `sqlite_master`. A SQLite FTS5 virtual table has shadow tables (`<name>_data`, `_idx`, `_content`, `_docsize`, `_config`); deleting rows from shadow tables by hand corrupts the index [U: SQLite FTS5 documentation, not re-opened]. The index must be dropped, not row-deleted.
3. `PRAGMA secure_delete` is already on for the phone database (`store.ts` `SECURE_DELETE_VACUUM_SETTING`) [R].
4. The device schema changes only by versioned migrations (DB-R25).
5. The export's golden files keep one frozen folder per earlier minor (`_v1.0.0` to `_v1.5.0`) [R].

## Decisions

### D1. The phone table: `entry_media` (migration 11) [P] [A]

One new local migration, version 11, in `apps/mobile/src/lib/db/migrations.ts`. This ADR first said 10; `develop` took 10 for the agreements table (`migrations.ts:393-394` at `09a104da`), so PR #796 appends 11 (`migrations.ts:428-469` at `39efe1ac`) [R]. It adds a table and three indexes only; no existing row changes; nothing is queued to the sync outbox (same shape as migrations 9 and 10). The table #796 creates matches the shape below column for column, with the level of each column in the migration comment [R].

```
entry_media
  id           TEXT PRIMARY KEY      media id, UUIDv7 made on the phone                    L2
  entry_id     TEXT                  the kept letter; null while only a draft owns it      L2
  draft_id     TEXT                  the draft; null once kept                             L2
  kind         TEXT NOT NULL         CHECK (kind = 'photo')   (video is not in Build 13)   L1
  ext          TEXT NOT NULL         CHECK (ext = 'jpg')                                   L1
  bytes        INTEGER NOT NULL      size of the stripped copy                             L1
  sha256       TEXT NOT NULL         of the stripped copy; a hash of a picture is L4       L4
  width        INTEGER, height INTEGER                                                     L2
  photo_text   TEXT                  the parent's own words, CHECK (length <= 140)         L4
  place        TEXT                  typed by the parent, CHECK (length <= 60)             L4
  added_at     TEXT NOT NULL                                                               L2
  CHECK ((entry_id IS NULL) <> (draft_id IS NULL))
INDEX entry_media_entry_idx ON entry_media (entry_id) WHERE entry_id IS NOT NULL
INDEX entry_media_draft_idx ON entry_media (draft_id) WHERE draft_id IS NOT NULL
UNIQUE INDEX entry_media_one_photo_idx ON entry_media (COALESCE(entry_id, draft_id))
```

Decisions inside it:

- **Class.** The picture itself is L4 (a child's image; `DATA_CLASSIFICATION.md`), the typed text and place are L4 (the parent's words), the ids and sizes are L2. `privacy` confirms; I label the columns in the migration comments in the same PR, as migration 9 does.
- **No `deleted_at` on the row.** PR #796's `StoredPhoto.deletedAt` copies a state the letter already owns. A copy can drift (letter restored, photo still hidden). The row is hidden whenever its letter's `entries.deleted_at` is set, by join; restore needs no photo write. The `PhotoStore` adapter maps `deletedAt` from that join. If the mobile engineer prefers the field, the adapter must still derive it, never store it. Default: derive.
- **Storage location is `Library/Application Support/photos/<media_id>.jpg` on iOS, and `<app files folder>/photos/<media_id>.jpg` elsewhere (Android, later).** [A] This ADR first said `Documents/photos`. Karma ruled that the security review wins (finding T5, quoted in #796 `lib/photos/files.ts:3-5`), and #796 builds it that way: `photosDirectory()` derives the folder from the Documents uri (`files.ts:20-27`) [R]. Why Application Support, from Apple's File System Programming Guide (opened 19 Nov 2026): Documents "can be made available to the user through file sharing" and should hold only files "you may wish to expose to the user"; the `Library` subdirectories are "for any files you don't want exposed to the user" and Application Support is for "all app data files except those associated with the user's documents". So a child's picture never appears in the Files app, whatever sharing setting a later build adds. The folder is kept across launches: it is not `Caches` or `tmp`, which the system may purge. Backup: Apple says the contents of Application Support "are backed up by iTunes and iCloud" unless a file is excluded with `NSURLIsExcludedFromBackupKey`; #796 makes no such call for pictures (the only `setExcludedFromBackup` callers on its branch are `lib/model-files.ts:43` and `lib/packs/app-support.ts:38`, for models and packs) [R], so the pictures are in the iPhone backup, the NX-39 F9 default (Q4). The file name is the media id, never an original name, and no entry id is in it. A draft keeps its id when it becomes a letter (the `mobile` note on PR #797; `adopt.ts:12-16` passes one `ownerId` for draft and letter) [R], so `draft_id` moves to `entry_id` in the same transaction as the letter and the file never moves (Q2 closed). The folder in the export is derived (D2; `types.ts:55`).
- **One picture per letter** is the unique index, not the table shape. Build 13 caps at one; a later multi-photo build drops that one index in its own migration (no table rebuild).
- **Backup.** The folder is not excluded from the iPhone backup (NX-39 F9 default: pictures in the backup); confirmed by the absence of any exclusion call under `lib/photos/` at `39efe1ac` [R] [A]. The owner backup of ADR 0024 does not carry pictures in Build 13 (audio only); `privacy` words that plainly.
- **Inventory row and the parent's words** [A2, review B must-fix 3]. DATA-REQ-001 (P0, `DELETION_AND_EXPORT_SPEC.md:51`) wants every device store in `docs/legal/data-policy.md` section 4 in the same PR; D4 does this for the index (below) and the same holds for pictures. The PR that ships pictures adds one row to section 4.4 Devices (`data-policy.md:134-145`), proposed text: `| Pictures: Library/Application Support/photos/<media_id>.jpg (the stripped copy) and the entry_media rows in the local database | app sandbox, Application Support, in the device backup (NX-39 F9) | C | Until the letter is purged, the draft is let go, Erase everything, or the app is deleted | Never uploaded (NS-01-R15); the export carries it (NS-01-R14, D2) |`, and the row at `data-policy.md:144` (iOS device backup: "recordings and the local database are included") gains pictures. `privacy` confirms class and wording. The parent-facing lines that must gain pictures when photos ship, so that no picture sits in an iPhone backup that no line mentions: `docs/legal/privacy-policy.md:37` ("Your recordings. Recordings are kept on your phone, and in your phone's own iPhone backup if you use one."; `:45` "we do not collect ... photos" stays true, the picture reaches no server) and, in `packages/content/src/strings.en.ts`, the keys `whereLive.onPhone` (`:1381`), `whereLive.onPhoneSynced` (`:1383`) and `whereLive.iphoneBackup.body` (`:1390`, today "Includes your recordings, if iCloud Backup is on."); and the keys that carry the same promise on the Recordings card and the Privacy page [A3, review B note]: `settings.recordings.onPhoneBody` (`:808`) and `.onPhoneBodyBackupOff` (`:811`), `settings.privacy.keptOnPhone` (`:1008`), `.keptSynced` (`:1010`) and `.iphoneBackup` (`:1014`, the same words as `whereLive.iphoneBackup`); `content` checks every one of them when photos ship. `content` also checks `packages/content/src/pages.en.ts:240` (account deletion: "letters, recordings and photos are removed from every book"), since pictures are on the phone only. This ADR names the lines, not the words: `content` writes them; counsel reads them (legal text is founder-merged).

Kill-safety order, each step safe to repeat [A]: (1) write the stripped copy whole to `Library/Application Support/photos/<id>.jpg` (#796 writes with `overwrite: true`, `files.ts:49-51`, no `.part` step; a half-written file has no row and is swept) [R]; (2) in one transaction insert the row; (3) at launch a sweep deletes any file with no row and any row whose file is missing (the letter then reads whole with no picture, no message, OQ-2 default). A cancelled pick writes nothing (NS-01-R4).

Sync: `enqueueEntryUpsert` and the pull merge never read or write `entry_media`, and the push mapper always sends `photo_path: null` (NS-01-R15). Pull must not overwrite a local row. Test below.

Migration plan [A]: migration 11 ships with photos (#796). Find (D4) has no migration: #798 creates its index with `CREATE VIRTUAL TABLE IF NOT EXISTS` from `ensureSearchIndex`, whose own comment says "Not a migration" (`lib/find/lifecycle.ts:169, 195-200`) [R]. The seal (D3) takes the next free number when it is built; two open PRs must never both claim a number, so the later one renumbers on rebase. A phone whose database is newer than the app (a downgrade) is not migrated: `migrate()` returns `{ newer: true }` and runs nothing (`migrations.ts:455` on `develop` at `09a104da`) [R] [A2].

For the #796 builder [A]: one comment line is stale. `apps/mobile/src/lib/db/migrations.ts:435` at head `39efe1ac` reads "The picture file is `Documents/photos/<id>.jpg`"; it must read `Library/Application Support/photos/<id>.jpg` (iOS; the app's files folder elsewhere), the same words as `lib/photos/files.ts:3`. Nothing else in the migration changes.

### D3. The sealed letter: should a seal sync? [P] [A]

Recommendation: **the seal syncs as columns on `entries` (D3a); the seal is a display rule on the author's own phones; and no other person's phone receives a sealed letter's row or words until the instant.** Build 15 at the earliest, behind the five-parent study (NS-06 OQ-B1); nothing here is built before then. The PRD at `6a11c808` (NS-06-B8) and design spec 04 section B6a already carry the author-only rule; only the clock was left open, and D3a answers it.

Why not the two simpler answers:

- A seal that stays on one phone fails the author on their second phone: the sealed letter appears open there, which breaks the promise the parent made (NS-06-B8 says no build if it cannot sync).
- A seal that syncs only as a date, with the words still pulled to a co-parent's phone, is a lock that is not a lock: the words sit in that phone's database. NS-06-B5 already forbids the words "locked" and "secure"; the data should match the copy.

Design:

- **Server:** three nullable columns on `entries`, additive, written by the author only (RLS as today): `seal_opens_at timestamptz` (the instant, NS-06-B1), `seal_opens_on date` (the day the parent chose, as typed, like `occurred_on`) and `seal_cleared_at timestamptz` (stamped by the server when the author chooses Open now; this ADR first called it `sealed_opened_at`, renamed because "opened" is also what the day does). All three L4 [A3, review B must-fix 1]: `DATA_CLASSIFICATION.md:49` lists sealed dates among the L4 examples and `data-policy.md:91` already classes the planned `entries.sealed_until` as A/C (C maps to L4 at `:49`); a day chosen for a milestone ("for your 18th birthday") states the child's birthday, itself L4 (`:49`, rule 6 at `:58`), the instant is derived from that day (rule 2 at `:54`), and `seal_cleared_at` is set only on a sealed row and says one existed, so it takes the same level (rule 1 at `:53`). This ADR first wrote L3; that was wrong. Storage: the three columns live on the author-only row (RLS as today) and `book_entries` never shows them, so no other reader's pull carries them. Access: `service_role` reads them only in `publish_opened_seals()` (D3, the job), and the export carries them for the author alone (1.8.0). The seal build amends the `data-policy.md:91` row, where `sealed_until` becomes `seal_opens_at`, `seal_opens_on` and `seal_cleared_at`, class C, and adds the three names to `mustBeL4` in `supabase/tests/classification.test.mjs:24`, so a migration comment below L4 fails CI; `privacy` confirms. A trigger `entries_12_seal_guard` (prefix per DB-R04) with its trigger function `entries_seal_guard()` (a new object, revoked from `public`, `anon` and `authenticated` in the same file, DB-R14; the pattern is `20261016000000_sync_v1_server.sql:2061-2064`) [A2] enforces the PRD: the pair may go from null to a value on a row that is a letter with words (never a quiet-day mark, NS-06-B10); a set pair never changes and never returns to null (the guard compares values, `new.seal_opens_at is distinct from old.seal_opens_at` and the same for the day, so a later write of the unchanged pair passes and only a changed pair is refused; Open now needs this, below) [A3, review A note]; `seal_cleared_at` is set to `now()` by the server when the client sends any non-null value, is never cleared, and is refused while the pair is null; every refusal carries one typed SQLSTATE (proposed `SCSEL`, registered in the error table of `docs/engineering/02-api-and-contracts.md:92-110` per API-R09, with `sync`). **A past instant is accepted** [A2, review A must-fix 2]. This ADR first wrote `seal_opens_at > now()` as a guard. Scenario it breaks: the author seals offline on day D for D+1 and reconnects on D+2; the push arrives after the instant, the guard refuses the op with `SCSEL` for good, and the letter never lands on the server. So the server accepts any instant on the first write and treats a past one as already open: the opening rule (D3a) is already true for every reader, `book_entries` passes the row to another reader at that reader's next pull, and the publish job never touches it (its predicate `updated_at < seal_opens_at` is false from the first write). A past day is refused where the parent picks it, at the control (PRD 06 B5, `docs/product/prd/06-firsts-sealed-letter-quick-capture.md:111`: "the control offers only later days"), not at the server. Meanwhile the author's phone shows what its own rule says: closed until the instant, then a normal letter, with no network; the late push changes nothing on screen. The CHECK `entries_seal_pair` (D3a) keeps the pair together. Re-seal is refused by construction: a non-null pair cannot change, and a cleared seal keeps its pair.
- **Visibility:** the one visibility predicate for another reader is the `book_entries` view (`20261003000000_security_and_family.sql:563-581`), which the pull uses for every row the caller did not write (`20261004100000_sync_engine.sql:372` as first built; the shipped `sync_pull` is `20261016000000_sync_v1_server.sql:1302`, the same clause at `:1505`) [R] [A2]. This ADR first named `book_access` (D-024) and `server_seq` (DB-R23); neither exists in `supabase/migrations/` at `09a104da`, so the shipped names are used here, and chapter 03's steward is told in the PR body that DB-R23 and the code disagree [A]. The view gains one clause for rows the caller did not write: `(e.seal_opens_at is null or e.seal_cleared_at is not null or e.seal_opens_at <= now())`. Until the instant the pull returns no row for the other reader at all, the same way a private letter is not sent (`sync_engine.sql:43-46`). The author's phones receive every own row, by its column list [A2, review A must-fix 1]: the pull builds an own row from an explicit column list (`20261016000000_sync_v1_server.sql:1481-1496`; this ADR first cited `sync_engine.sql:353`, whose `sync_pull` was replaced since) and the push inserts and updates an explicit list by field group (`sync_v1_server.sql:936` names the groups, `:1091-1096` the insert list); the contract enumerates the same (`packages/api/src/server/sync.ts:94-104` `FIELD_GROUPS` and `FIELD_GROUP_COLUMNS`, `:263-267` `ENTRY_DATA_KEYS`) and the phone maps rows column by column (`apps/mobile/src/lib/sync/outbox.ts:161-184` `entrySnapshot` for the push, `merge.ts:489-495` and `:643-654` for the pull) [R]. A column none of them names never travels. ### D3a. The seal clock: one stored field or two [P] [A]

The question (`NEW-SCOPE-INDEX-11nov.md` section 8, the `data-architect` row; NS-06-B1 and OQ-B2; design 04 FS-R7 and the B6 clock rows; design 02 FD-R9; answer due Fri 20 Nov 2026): the PRD stores one absolute UTC instant, the author's local midnight at the start of the chosen day in the device's zone at sealing; D3 as drafted stored a calendar date with a UTC-plus-one-day grace for other readers. One field or two? This section is a proposal for Karma's acceptance after two reviews; until then FS-R7, the 04 B6 clock rows and 02 FD-R9 stay PROVISIONAL, as the index says.

Three ways, weighed:

1. **One calendar date, opened by the local date at read time** (D3 as drafted). Rejected. A flight east or a zone change opens the letter up to 26 hours early (UTC-12 to UTC+14), which FS-R7 forbids, and the server's grace day opens it for others at a different moment than for the author: two clocks for one promise.
2. **One instant only** (NS-06-B1 as worded). Rejected as the only field. The rule is exact and the same on every device and on the server (compare with now). But the words the author reads, "hidden until <day>", would have to be derived from the instant in the reader's current zone, and that is the wrong day whenever the reader is west of the sealing zone (the day before) or more than 24 hours east of it (the day after). Example: sealed in London for 10 Jan, stored `2027-01-10T00:00:00Z`, shown in New York as 9 Jan. Storing a zone id to fix the words would add a datum the parent never typed, to derive what the chosen day states directly (minimality; see Alternatives) [A2].
3. **The instant and the chosen day, both written once in the same statement and never updated** (CHOSEN). The instant is the rule; the day is the words. Drift is impossible by construction: neither column may change once set (the trigger, as for `raw_transcript`), and the CHECK keeps the instant inside the window of real-zone midnights of the chosen day (UTC+14 to UTC-12) [A2]. The day adds nothing the author did not type.

Schema (server, additive to `entries`; every column L4 [A3, review B must-fix 1; D3 gives the reason]; written as a migration only when the seal is built, timestamped after the newest file in `.github/migrations-applied.txt` (DB-R08) and after the newest file in `supabase/migrations/`, `20261109000000_child_name_optional.sql` at `09a104da`, so it sorts last [A2]):

```
seal_opens_at    timestamptz  null   the instant: local midnight at the start of the chosen day, in the
                                     device's zone at sealing, kept in UTC (NS-06-B1)                  L4
seal_opens_on    date         null   the day the parent chose, as typed (the words; like occurred_on)   L4
seal_cleared_at  timestamptz  null   server-stamped when the author chooses Open now; never cleared     L4
CHECK entries_seal_pair (
  (seal_opens_at is null) = (seal_opens_on is null)
  and (seal_opens_at is null
       or seal_opens_at between (seal_opens_on::timestamp at time zone 'UTC') - interval '14 hours'
                            and (seal_opens_on::timestamp at time zone 'UTC') + interval '12 hours')
  and (seal_cleared_at is null or seal_opens_at is not null))
INDEX entries_seal_due_idx on entries (seal_opens_at)
  where seal_opens_at is not null and updated_at < seal_opens_at      -- the publish job; a row leaves it once published
```

The CHECK says what the pair means [A2, review A note]: the instant lies in the window in which some real zone has its midnight of the chosen day, from UTC+14 (14 hours before that day's UTC midnight) to UTC-12 (12 hours after it). This ADR first wrote "within one day of each other", which is looser; the new form implies that rule. It does not check that the instant is a local midnight at the sealing zone's offset, whole or half hour (UTC+5:30 Kolkata and UTC+9:30 Adelaide exist, so "whole hour" would fail there); the device test does, with zone injection [A3, review A note]. Names follow DB-R01: `_at` for an instant, `_on` for a date; the shared stem `seal_opens` ties the pair. `comment on column` carries each level (DQ-R01). Device mirror (DB-R25; the next free local migration when built, with the level of each column in the comment as migration 11 does): `entries.seal_opens_at TEXT` as `YYYY-MM-DDTHH:MM:SSZ` (whole seconds; the instant is a midnight), `entries.seal_opens_on TEXT` as `YYYY-MM-DD` (like `occurred_on`, `migrations.ts:67`), `entries.seal_cleared_at TEXT`; `drafts` carries the pair from Review until Keep copies it to the letter; index `entries_seal_idx ON entries (seal_opens_at) WHERE seal_opens_at IS NOT NULL AND seal_cleared_at IS NULL` for the Book's closed rows and the launch catch-up. No zone id is stored, and what is stored says this much [A2, review B must-fix 1]: `seal_opens_at` is a local midnight kept in UTC, so its time of day is the sealing zone's UTC offset on that date (`08:00:00Z` below reads UTC-8). That is inherent to NS-06-B1's instant, not added by the second column; it is coarser than a zone id (a few dozen offsets against hundreds of zones) and says nothing beyond the offset. It is L4 with the pair it belongs to (D3; `DATA_CLASSIFICATION.md:49`, and rule 1 at `:53`: a row takes the highest level of its columns) [A3, review B must-fix 1] and author-only: `book_entries` never exposes the three columns (D3), so another reader never sees it, and co-parent sharing is later in any case (D-121). It is the same kind of datum as two columns every letter already carries, `occurred_on` beside `captured_at` (`20260930000000_scribe_core.sql:125-126`): a day the parent chose beside a UTC instant. A `service_role` reader can read the offset from every sealed row, and the only server code that does is `publish_opened_seals()` (D3). Counsel should not brief the seal as location-free; the exact comparison [A3, review B note]: the seal row states the sealing zone's offset exactly, a letter's `occurred_on` beside `captured_at` only bounds it to a window because `captured_at` is not a midnight, and both are less than the IP address every sync already shows the server.

The opening rule, one sentence: a letter is open when `seal_opens_at IS NULL OR seal_cleared_at IS NOT NULL OR seal_opens_at <= now()`, where `now` is the current UTC instant and never a local date; the same expression is the one visibility function on the phone (NS-06-B6), the clause added to `book_entries` on the server (D3) and the clause in `searchable_letters` (D4).

How the instant is made, on the device at sealing: take the chosen `YYYY-MM-DD`, find the start of that day in the device's zone at that moment, convert to UTC, and store it beside the date. FS-R7's case: sealed in UTC-8 for 10 Jan gives `seal_opens_at = 2027-01-10T08:00:00Z` and `seal_opens_on = 2027-01-10`; at UTC+14 with the clock at `07:59:00Z` the letter is closed, at `08:00:00Z` it is open, and the row still says 10 Jan.

What each reader and surface reads:

- **The words** ("hidden until <day>"; `content` owns them): `seal_opens_on`, rendered as a date in the reader's locale; never computed from the instant.
- **Find:** `searchable_letters` reads `seal_opens_at` and `seal_cleared_at` (the opening rule), never the date (D4).
- **Export (1.8.0, author only):** all three fields, by their column names. PRD NS-06-B5 names one `sealed_until` field; that row should read as this pair plus the cleared time, and `product` aligns it in one line (Q10).
- **Another reader:** nothing before the instant; a normal letter after it, with no seal columns (D3).

The considerations Karma named:

- *The author travels across zones before the day:* the instant does not move (NS-06-B1b), so the letter never opens before the start of the chosen day where it was sealed, and the Book row keeps saying the day chosen. Honest limit, and `content` must word it, not may [A2, both reviews]: in a zone west of where it was sealed the letter opens during the evening before the shown day, local time. No stored-field design removes this: a reader-local "later of the two" rule cannot run in `book_entries` or in the job, and would reopen the FS-R7 case; so the words say it rather than the data pretending otherwise. Also for `content`: a clock set forward by hand opens it early on that phone, and the app does not claim to prevent that (NS-06 B5).
- *The co-parent in another zone (co-parent sharing is later, D-121):* no row before the instant (NS-06-B8); after it, a normal letter through the publish job (D3), the same instant for everyone, no grace day.
- *Export and Find:* above. Find reads the instant, so the index needs no local-date logic and no time-zone case.
- *The letter is author-only until it opens:* true for the row and the words; the seal columns reach only the author's own phones, backup and new-phone restore before the instant (NS-06 B6, the Records line).
- *The words users read:* the chosen day, stored, so what the parent typed is what the parent reads.

Tests on the device, when built (each titled with its id): `[NS-06-B1]` sealing writes the pair and nothing else about the words; `[NS-06-B1b][FS-R7]` the UTC-8 to UTC+14 case with clock and zone injection; the row says the chosen day in three zones; `[NS-06-B3]` Open now sets `seal_cleared_at` and the letter reads at once; a second seal on the same letter is refused; `[NS-06-B6]` one visibility function, call sites listed; `[FD-R9]` the index moves at Open now in the same transaction and at the instant on the next `reconcileSearch`, and a zone change leaves the index unchanged; the export of a sealed letter carries the three fields for its author and nothing for another reader; `[NS-06-B10]` a quiet-day mark cannot carry a seal.

### D4. Find index: storage and lifecycle [P] [A]

- **Where:** an FTS5 virtual table `letter_search` inside `scribe.db` (one file, one lock, iOS Data Protection covers it, `secure_delete` already on). Not a second database file.
- **Shape:** its own content (not external-content), columns `body` (the `final_text` as kept) and `extra` (the parent-typed Firsts label, photo text and typed place), tokenizer `unicode61 remove_diacritics 2` (#798 creates it so, `lib/find/lifecycle.ts:169`; PRD NS-02 section 10 says `expo-sqlite` 57.0.3 compiles FTS5 by default, so no config change, UNVERIFIED on a phone) [A]. ## Alternatives considered

- Store the picture as a BLOB in `scribe.db`: rejected; it bloats the database and its VACUUM and backup cost, and the file is easier to erase and sweep.
- Put `photo_path`, `photo_text` and `place` on `entries`: rejected; it fixes one picture per letter into the synced table's shape and invites the sync mapper to carry them.
- External-content FTS5 table: rejected; the delete path needs the old values, and visibility is not a column.
- SQL triggers for the index: rejected for the seal and hide cases, because visibility changes with the date, not with a row event. One function plus a launch catch-up is simpler to test.
- Server-enforced seal only for the author's phones: that is the default above; the stronger "no row at all for others" is chosen because a display rule cannot honestly protect words that already sit on another phone.
- One calendar date, or one instant only, for the seal clock: rejected in D3a (the first opens early across zones; the second shows the wrong day west of the sealing zone) [A].
- The IANA zone beside the instant, to derive the day: rejected for minimality, not as a location leak [A] [A2]. A zone id is a region, coarser than the IP address the server sees at every sync, so it would leak little on its own; but it is an L3 datum the parent never typed, stored to derive what `seal_opens_on` states directly, and the instant already carries the zone's offset (D3a). The chosen day is what the parent typed, so the day is the column.
