Each numbered decision takes effect when the founder accepts it (in this PR's review or in writing); decisions 1 to 3 are founder settings, not file changes.

- **Builds on:** ADR 0022 (release engineering: two lanes, version in `apps/mobile/version.json`, EAS build numbers, RC tags on `release/*`, EAS Metadata for store text, the `app-store` environment, no OTA), D-041 (migrations reach hosted projects only through CI), D-089 to D-092, D-097 (pack host), D-100 (server features on after the R-17 gate), D-106 (alpha against staging), D-107 (founder-only merges and production deploys), and the alpha plan on #152 (founder steps F01 to F27).

Labels there: [V] verified on the vendor's own page or source, [V-S01] and [V-QA] verified by a reviewer, [R] repo fact, [U] unverified.

## Context

The founder asked for "proper actions and journey to automate everything". The sandbox agents work in cannot reach expo.dev or App Store Connect, so every build, submission and store action must run in GitHub Actions, started by an agent through `workflow_dispatch` and read back from run logs. Secrets live only in GitHub environment secrets and EAS. Production actions and real-data actions stay founder-only (D-107), as one approval click.

Facts found on 16 Oct 2026 that shape the design:
1. **Agents act as the founder.** Agent sessions use a token for the founder's own account; an environment approval record carries only the user; the owner account can re-add itself as a reviewer and bypass rulesets [V-S01]. So while the founder's account is a required reviewer, "agents never approve" is a written rule, not a control.
2. **Nothing protects `main` or `develop`** [R: GitHub API]. A push to `main` is a website production deploy.
3. **The default branch is `main`** [R], and `main` holds only `ci.yml`, `migration-guard.yml`, `web.yml` and `web-e2e.yml` [R]. GitHub runs `schedule` and `workflow_dispatch` only for files on the default branch, and runs `pull_request_target` and `issue_comment` from it on github.com [V]. So `testflight.yml` cannot be dispatched and `nightly.yml` never runs; `claude.yml` (its gate was `author_association == 'OWNER'` alone, which agent comments pass [V-S01]; RA-20-02a adds `performed_via_github_app == null` and refuses fork heads) goes live for comments and opened issues when the default branch changes; its review triggers already ran each pull request's own copy of the file (SECRETS_REVIEW SR-1) until RA-20-02a removed them.
4. **`pull_request_target` is blocked by default in public repositories from 2 Nov 2026** unless an Actions event policy allows it [V]; the fence in #30 uses it.
5. **The two lineages diverge.** `apps/web` exists only on `main`; the Vercel project's root directory is `apps/web`, so every preview of a `develop`-based branch fails at `build-container-init` [R: deployment `dpl_3fbe7smLCY5TzbuQHR8zJLvrm98b`].
6. **App Store Connect** [V: Apple API reference]: the API covers TestFlight groups, Beta App Review, What to Test, build expiry, screenshots, review submissions, phased release and TestFlight feedback (whose attributes include the tester's `email` and `comment`), and has no App Privacy resource. Team keys reach every app on the account whatever their role. Internal testers can read every tester's feedback, and the Developer role can add builds to internal groups but is read-only on external groups [V-QA, V-S01]. When `eas credentials` creates a key it offers "ADMIN (default)" and "APP_MANAGER" [V: eas-cli source].
7. **EAS:** Metadata is beta and does not upload screenshots [V]; a Developer-role token can make builds and manage credentials and cannot be limited to one profile [V]; the Free plan's iOS build allowance is small (15 a month per D-092 [U today]).
8. **Supabase:** paid projects cannot be paused; publishable keys are created, named and revoked independently, and legacy keys can be deactivated [V]. `supabase db push` seeds nothing here (`[db.seed] enabled = false` [R]). The agents' Supabase connector sees every project in its organization and can run SQL; the Vercel connector can promote and roll back [V-S01, R].
9. **The repository is public**, so Actions logs and issues are public. TestFlight feedback can carry a child's name or a letter's words.
10. **GitHub Free on a public repository** includes environments with required reviewers, prevent self-review, deployment ref rules, an option to stop administrators bypassing, rulesets and protected branches; standard hosted runners, macOS included, are free [V].

## Decision

1. **An approver account.** Withdrawn 31 Oct 2026 (`docs/agents/cto/RULINGS.md` CR-19): GitHub's Terms allow one free account per person plus one free machine account "used exclusively for performing automated tasks", so a second personal account for the founder is not an option. The separate identity goes to the agents, not the founder (CR-20). Original text: a second GitHub account, held only by the founder (passkey, never connected to claude.ai, a connector, a CLI or an agent machine), is the **only** required reviewer on every environment that has one, with "Prevent self-review" on and "Allow administrators to bypass" off (AF-02). Until it exists, every "the founder approves" in the plan is policy, not enforcement. A drift job compares the environments with a committed expected file, and a monthly reminder covers the bypass switch the API does not show. The durable fix, agents no longer holding the owner credential (an organization owned by the approver, or a Write machine user), is a founder decision after the alpha (AF-27).
2. **Branch protection on `main` and `develop` now** (AF-03; as applied by CR-7 on 31 Oct: 0 required approvals, because every PR author is the owner account, CR-20): pull request required, `required` and `applied migrations unchanged` required, no force push or deletion, no bypass; on `main` one approving review by the approver. After the alpha, CODEOWNERS names the approver for D-107's founder-only paths and code-owner review turns on (AF-21).
3. **`develop` becomes the default branch** (AF-05), only after `claude.yml` is hardened (`performed_via_github_app == null`, no fork heads, SHA pin; RA-20-02a) and Vercel's Production Branch is confirmed as `main`. Before Mon 2 Nov, or before #30 merges if sooner, an Actions event policy allows `pull_request_target` for `.github/workflows/fence.yml` only (AF-20).
4. **One lineage, after the alpha.** One founder-merged PR brings `main` into `develop` (RA-20-01, the `docs/DEVELOPMENT.md` merge-back rule). Until then the Vercel status on `develop` PRs is never a required check.
5. **Eight GitHub environments**, each with deployment refs restricted: `staging` (approver; `develop`, `main`), `production` (approver; `db-v*` tags), `testflight` (`develop` only; the approver until AF-21 is in force, then none), `testers` (approver), `app-store` (approver; ADR 0022), `packs` (approver; `develop` only), `health` (none), `agents` (none; `develop` only; the harness secrets move here from repository secrets). Expo tokens come from robot users, never personal tokens. The repository `EXPO_TOKEN` stays until the workflow that reads its replacement has merged and one dispatch with it is green. Every secret-holding job runs `npm ci` without the restored `node_modules` cache.
6. **TestFlight.** For the alpha the founder adds builds to groups by hand with automatic distribution off; no automation adds a build to "Friends" before the R-17 sign-off. After the alpha, `testflight.yml` v2 builds into the internal group "Founder" only, stops at a build cap set two builds below the plan's allowance, and lets a `kill-path` build of the servers-off profile skip the cap. "Founder" and "Family" are internal groups; **"Friends" is external**, through Beta App Review. Promotion runs in `testers`, which refuses a servers-on build (decided from the build commit's `eas.json`, failing closed) for anyone outside "Founder" and "Family" unless both the `testers` variable `R17_PASSED` and the "R-17 passed" entry in `docs/DECISIONS.md` say so. Agents never set or change a variable.
7. **App Store Connect access is split by job.** Keys `gha-testers` (App Manager, `testers`), `gha-release` (App Manager, `app-store`) and `gha-feedback` (Developer, private feedback repository), each revocable alone; individual keys of a dedicated App Manager user limited to the two app records are the stronger option. The key EAS creates is App Manager, never the Admin default. One small TypeScript client in `scripts/release/asc/` covers groups, Beta App Review, expiry, screenshots, review submission and phased release; store text stays on EAS Metadata (ADR 0022 decision 6); fastlane is not adopted (Ruby toolchain, and its App Privacy action needs an Apple ID session) except as a fallback for the screenshot job. App Privacy answers stay manual.
8. **Pack signing never moves to CI** (#162). The founder signs on their own computer and commits the signed documents; `packs-publish.yml` in `packs` rebuilds the unsigned files keylessly, checks every signature and hash, and uploads with the bucket-scoped token. A CI-held key, even for remote config only, is not offered.
9. **Tester feedback stays private.** A poller in a private repository reads feedback through the API; public issues carry content-free crash pointers only. The external group's feedback address is a dedicated mailbox no connector reads; the Claude and agents GitHub Apps are installed on selected repositories only, never on the private one; testers are told that other testers on the team can see their TestFlight feedback.
10. **Connectors are production credentials.** Staging and production Supabase live in an organization the agents' connector is not authorized for, or the connector is read-only and scoped to a development project (AF-06). Vercel production promotes and rollbacks are founder actions. Agents never use connectors against staging, production or the founder's inbox.
11. **What agents may start.** The coordinator dispatches `testflight.yml` and `release-cut.yml`; any agent may dispatch the compile check, nightly, e2e, kill harness, health and advisors. Agents never dispatch deploy, publish, testers or store workflows, never approve, never change settings, secrets or variables, and push only the coordinator's RC and `db-v*` tags, which do nothing until the approver approves.
12. **Health is scheduled and content-free**: probes four times an hour off the hour, advisors weekly through a catalog-only database role, a red nightly opens one issue, one issue per failing check, closed when green.

## Alternatives considered

| Option | Why not |
|---|---|
| The founder's own account as the only reviewer (revision 1) | Agents act as that account, so GitHub cannot tell their approval from the founder's |
| Keep `main` as default; copy workflow files onto `main` | Every workflow change needs two merges, and `main` is the live website branch; a stale copy on `main` silently governs dispatch, schedules and the fence |
| Merge the lineages before the alpha | Adds `apps/web` to the root tests and typecheck every alpha build runs, during the R-17 batch |
| Fix Vercel with `git.deploymentEnabled` in `vercel.json` | The file is read from the root directory of the branch being deployed; `develop` has no `apps/web` |
| Disable Vercel preview deployments | Stopgap only; loses website previews on `main` PRs |
| No reviewer on `staging` (DEPLOY.md) | Staging holds family letters during the alpha |
| Pause staging as the emergency stop | Paid projects cannot be paused; revoking the alpha builds' named publishable key works instead |
| Friends as internal testers (#152 F26) | Internal testers read every tester's feedback, and the Developer-role feedback key could add a servers-on build to their group |
| One App Store Connect key for every job, or the Admin key eas-cli offers by default | A leak reaches every app with the widest role, and no job's key can be revoked alone |
| fastlane `deliver` and `pilot` for all store work | Covers most of it with an API key, but adds Ruby, duplicates the EAS Metadata path already built (#109, #110) and its App Privacy action needs an Apple ID session |
| EAS Workflows instead of GitHub Actions | A second pipeline outside our checks and environments (ADR 0022 rejected it); agents cannot reach expo.dev to read its logs |
| App Store Connect webhooks into GitHub | Needs a public HTTPS receiver holding a GitHub token; polling needs neither |
| Signing key as a CI secret, in full or for remote config only | A CI-held config key could raise `minSupportedVersion` and force every installed app to update; uploads need only the bucket token |
| Feedback text in public issues | The repository is public; tester text can hold a child's name (CLAUDE.md privacy rules) |

## Consequences

- **Until AF-02 is done, the approval rule is policy, not enforcement.** After it, approvals are enforced, but the owner credential in agent sessions can still change repository settings; the drift job, the monthly bypass look and AF-27 cover that. S01 reads the settings back (RA-01-01) before any secret is added.
- The approver's recurring clicks: `staging` deploys after migration merges, `testflight` builds until AF-21, `testers` promotions and Beta App Review, `app-store` jobs, `packs` uploads, merges into `main`.
- After AF-21 the `testflight` token is guarded by the `develop` ref rule, branch protection and code-owner review only; a Developer-role robot token can still make builds and manage credentials in EAS if a job on `develop` leaks it. Accepted, with the token in one environment and reviewed in `ops-reminders.yml`.
- Builds draw on EAS's monthly allowance (D-092). The cap keeps two builds of headroom for the servers-off undo; past it the founder moves to Starter (19 USD a month with 45 USD of build credit [V]). Simulator builds for the compile check, kill harness, e2e and screenshots run on the free macOS runner, not on EAS.
- The staging stop is revoking the named publishable key the alpha builds use; recovering needs a new build. It is rehearsed on a scratch project before staging holds letters.
- Vercel Hobby is for non-commercial use; Pro is a founder prerequisite (AF-15).
- Edge Function deploys from CI need a scoped Supabase token (public alpha [V]); without one, functions deploy from the founder's computer and the workflow says "NOT DEPLOYED".
- The founder's hands-on time before Thu 29 Oct grows by about two hours over #152's 34 (AF-02, AF-03, AF-05, AF-06 extras, AF-07, AF-11, AF-14, AF-15).
- Export compliance (`usesNonExemptEncryption: false`) is re-assessed before a build ships app-level encryption of recordings (#150) [U: counsel].
