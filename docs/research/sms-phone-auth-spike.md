5. The per-IP number (BL-1943 item 3). Read: `auth_rate_limits.mdx` row 5 gives sign-ups and sign-ins, including `/auth/v1/otp` and `/auth/v1/user`, "Limited By: IP Address", "Defaults to [30] requests per 5 minutes, with bursts up to [30]"; in `apilimiter.go` lines 233 to 238, `Otp` and `User` (with `Recover`, `Resend`, `MagicLink`, `Signups`) are built by `newLimiterPer5mOver1h(gc.RateLimitOtp)`, which sets rate `rate / (60 * 5)` and `SetBurst(30)` (lines 358 to 363); `configuration.go` line 496 gives `RateLimitOtp` default `30`. So a phone send (`/otp`) and the phone change call (`PUT /user`, `api.go` line 294) are each limited to 30 per 5 minutes per IP, which is 360 an hour. That is far above the project cap of 30 SMS an hour (line 491), so the per-IP limit is not the control that stops pumping. The one key (`GOTRUE_RATE_LIMIT_OTP`; `apilimiter.go` lines 92 to 97 map `Otp`, `User`, `Recover`, `Resend`, `MagicLink` and `Signups` to it; that config.toml `sign_in_sign_ups` feeds it is not read [UNVERIFIED]) also sets email sign-in, so it cannot be lowered for phone alone. Lowering it below 30 does not lower the burst: `SetBurst(30)` is fixed in code (line 362), so a fresh IP can still send 30 requests at once. The limiter header the IP comes from on the hosted project, and whether each endpoint has its own bucket (the code builds separate `Limiter` objects, which suggests it) were not confirmed [UNVERIFIED]. Recommendation: leave 30 per 5 minutes and make per-IP the LAST control, not the first (order in section 7 item 2). It is the weakest against SMS pumping: attackers rotate proxies, and mobile carriers put many real people behind one address, so a low number refuses real parents while a high one stops nothing. The Send SMS hook cannot count by IP: the payload read (send-sms-hook.mdx, section 3 item 3) carries only `user` and `sms`, no request IP. A per-IP count therefore needs a gateway or an edge function in front of `/auth/v1/otp` and `PUT /auth/v1/user`; that is a new component and is not designed here. Any IP counter is a stored IP and meets `docs/legal/privacy-policy.md:153` ("We do not keep the IP address") and GEO-4 (`docs/regulatory/signup-geo-checks.md`, point 7 and row 9): it must be short-lived, keyed by a salted hash, never written to a durable table, and have privacy sign-off before it exists. A starting figure of 5 texts per IP per hour is ours and unmeasured [UNVERIFIED].

Our `supabase/config.toml` today: no `[auth.sms]` section, no `[auth.rate_limit] sms_sent`, and `phone_changed` notice is `enabled = false` (line 129; the BL-1943 row says it is on, which the file contradicts). On: `identity_linked`, `email_changed`, `identity_unlinked`. The test `supabase/tests/auth_config.test.mjs` pins auth values and has no SMS pin.

## 6. Cost model (assumptions, not vendor prices)

No vendor price was read, so the price is a variable `p` (cost of one delivered text, in the founder's currency, including any per-message carrier fee the vendor adds). Fill `p` from the chosen vendor's own pricing page at BL-1898.

Assumptions (ours, to be replaced by real numbers):
- A: new accounts per day who reach the phone step. Starting values to test: 50, 500, 5,000.
- Attempt share `s`: share of those who start the step = 0.4 (Phase A is optional; Not now is as large as Continue, R22). Our guess, unmeasured.
- Sends per started attempt `r` = 1.3 (some resends). Our guess.
- Daily cost = A x s x r x p. Monthly = 30 x that.
- Pumping ceiling with Supabase's cap `C` per hour: daily worst case = 24 x C x p. At the Supabase default `C` = 30 this is 720 p per day; at `C` = 10 it is 240 p.
- Spend alerts carry counts only (BL-1943 item 4): an alert, a dashboard note or a message to the founder says how many texts were sent and what share of the cap is used. It never carries a phone number, a code, a country-by-number list or any part of the message body, because those are R26's "no number in logs" and an alert is a log that people forward. The same holds for the Send SMS hook's error alerts. Alerts go only to channels we own. Vendor-console emails and delivery receipts may carry numbers and are outside our control [UNVERIFIED]: switch their content off or route them away from shared inboxes once the vendor is read. Small per-country counts are floored or rounded (for example under 10 shown as "fewer than 10"), because a count of one is a person.
- Pause trigger (card, R37): pause the step at 80 percent of the monthly cap. Set the vendor console cap at the monthly spend the founder accepts and set `C` so 24 x C x p is below one day's share of it.

| Accounts per day (A) | Texts per day (A x 0.4 x 1.3) | Texts per month | Monthly cost |
|---|---|---|---|
| 50 | 26 | 780 | 780 p |
| 500 | 260 | 7,800 | 7,800 p |
| 5,000 | 2,600 | 78,000 | 78,000 p |

The founder can read the monthly cost for any vendor by multiplying the right column by `p`. A hard cap in the vendor console is the second layer behind `C`.

## 7. Recommended Supabase settings for the build (BL-1898 and the build row apply them)

These are values to carry into `supabase/config.toml` and the hosted dashboard. This page changes neither.

1. Block unauthenticated phone `/otp` and `resend` (default, BL-1943). Read, `otp.go`: `Otp` sets `CreateUser: true` as the default (line 65); `shouldCreateUser` (lines 211 to 238) looks the user up only when the client sends `create_user=false`, so by default a registered, confirmed number goes to `sendPhoneConfirmation` and is texted a code (line 194, in the branch from line 187; lines 139 to 186 are the new-user Signup branch), while an unknown number goes to `Signup` and, when signup is off, is refused with a different error (`signup.go` line 116 `signup_disabled`, mapping from `auth.sms.enable_signup` not read [UNVERIFIED]). So `enable_signup = false` alone makes `/otp` an oracle for which numbers have accounts, and anyone can make us text any registered number with no account to count against, which is the main pumping route; the per-number and per-account caps below have nothing to count unauthenticated. Default design: an ALLOW-LIST at a gateway or edge function in front of Auth (a Send SMS hook refusal is a weaker option, see below). Allow only `PUT /auth/v1/user` with a phone and `verify` type `phone_change`, both for a signed-in session. Refuse everything else that carries a phone or can text one. Read, each of these reaches `sendPhoneConfirmation` with no more than the Phone provider being enabled: `POST /signup` with a phone (`signup.go` line 152 gates only on `External.Phone.Enabled`; line 271 sends, and it needs no session); `POST /otp` (`otp.go`, above); `POST /resend` type `sms` (`resend.go` line 141) and type `phone_change` (line 155, which re-texts the pending number set by an earlier `PUT /user`); `POST /reauthenticate` (`reauthenticate.go` lines 36 to 47: it texts the account's own phone only when the account has no email, and needs a session); and `verify` type `sms`, which turns a confirmed number into a sign-in door. So the list is: block `/signup`, `/otp`, `/resend` and `/verify` type `sms` with a phone for EVERY caller (not only for new numbers, because a confirmed phone is otherwise a way in for anyone holding the number, which R37 and item 9 forbid); block `/reauthenticate` for phone-only accounts (we have none: every account has an email) and allow `/resend` type `phone_change` only inside the per-account cap below. Required before any build, local test with `auth.sms.test_otp` (no real send): (a) for a known number and an unknown number, each of `/otp`, `/signup`, `/resend` and `/verify` type `sms`, with no session, returns the same body, the same status and the same timing, and sends no text for either; (b) `updateUser({phone})` plus `phone_change` still works while signed in. Test (a) will probably fail on native Auth alone, so the gateway block is the design, not a fallback. Hook fallback, [UNVERIFIED] and not a working design: refuse any send not tied to a `phone_change` of a signed-in user. The hook payload read carries only `user` and `sms` (section 3 item 3), so whether the hook can tell a `phone_change` send from a sign-in send was not read; do not rely on it until a test shows it. If neither works, the phone step stays off (R37).
2. `[auth.rate_limit] sms_sent`: a trade-off, not a safe default. At 10 per hour the cap is 240 texts a day, below the 260 a day of the 500-accounts case in section 6, so real people get blocked, and an attacker can burn the hour on purpose. Choose `C` from the expected peak hour with headroom, alert at 50 percent of the vendor monthly cap, and show the R27 fallback when it trips. Pin it in `auth_config.test.mjs`.
   R24 asks per-number, per-IP and daily project caps. Build order, strongest first:
   1. The project `sms_sent` cap plus a hard spend cap in the vendor console (the second layer, section 6).
   2. A country allowlist in the Send SMS hook, checked before any fee is paid (a signal under R29, never a refusal alone).
   3. Per-number and per-account daily caps counted on the server (hook or database), not on the phone; they only work once item 1 above makes every send belong to a signed-in account. Two limits. First, `user.go` lines 142 to 147 refuse a duplicate number with `phone_exists` before any send, so a signed-in account can probe which numbers are registered with no text sent: the per-account cap must count refused probes as well as sends (suggest 5 attempts a day per account, a proposal). Second, account creation is free (a free email or Apple account reaches `PUT /user`), so per-account caps alone do not bound spend or probing: an attacker makes many accounts. Item 1's `sms_sent` cap and the vendor hard cap stay the real ceiling, the 5 an hour per IP (item 6, gateway) slows account farming, and a new account may be held from adding a number for a short wait (suggest 24 hours after creation, a proposal).
   4. A velocity check on distinct numbers per account (one account asking for many numbers is the pumping shape).
   5. CAPTCHA only if design agrees to the screen (section 4).
   6. Per-IP last, with the limits above: gateway or edge function, short-lived hashed counter, privacy sign-off.
   Supabase gives only the hourly project cap, the per-user 60 s wait and the per-IP 30 per 5 minutes (loose); 2 to 4 are ours, owned by the data architect and platform. Until they exist the phone step stays off.
   The five-wrong-tries pause must be counted on the server (hook or database); a count on the phone is not a control. If a 10-minute code lifetime cannot be set natively (section 4), R24 fails natively and needs the hook or the step stays off.
3. Keep `sign_in_sign_ups = 30` and `token_verifications = 30`.
4. Code lifetime at 10 minutes or less on the hosted project (hosted field name [UNVERIFIED]); local CLI has no key for it.
5. Phone-change notices (BL-1943 item 1). Read, `verify.go` lines 473 to 478: after a `phone_change` verify, if `PhoneChangedEnabled` is on, the user has an email, and the old and new phone differ and the old one is not empty (`phoneNumberChanged`, line 827), Auth sends the notice to the account email; a send failure is logged and does not fail the verify. Gaps: (a) the first number added (old phone empty) sends NO `phone_changed` notice; `identity_linked` fires instead (lines 481 to 486), and its subject in config.toml says "Sign in with Apple is now on your account" for any provider that is not google; (b) nothing goes out at request time, only after the code is verified, so by then the number has changed; (c) an account with no email gets no notice at all (the `GetEmail() != ""` test). Turning the key on is not enough. Build list (a proposal; config.toml is not edited here):
   - `[auth.email.notification.phone_changed] enabled = true` with `subject` and `content_path` (keys at `cli_v1_config.yaml` lines 1025 to 1076).
   - A request-time email to the account email when a number is requested, sent from the Send SMS hook for the `phone_change` case or from an `auth.users` trigger (whether the hook can identify a `phone_change` send from its `user` and `sms` payload, and whether `auth.users.phone_change` is set at request time, were not read: both [UNVERIFIED]), rate limited per account (suggest 3 a day, a proposal) so it cannot be used to spam the inbox. It carries no number and no code, and a "not you" link that is single use, expires (suggest 24 hours, a proposal), never shows the pending number, and cancels the pending change and signs out other sessions.
   - Reauthentication before a number is added or changed (Auth has a reauthentication email, config.toml `[auth.email.template.reauthentication]`; whether `updateUser({phone})` can require it was not read [UNVERIFIED]).
   - A rule for accounts with no email: no number may be added until an email exists, or the step is refused with words.
   - A phone branch in the `identity_linked` subject and `templates/identity_linked.html` (content owns the words).
   - A notice on number removal. Whether `identity_unlinked` fires for a phone identity was not read [UNVERIFIED]; until read, treat removal as unnotified and send our own.
   - A hold, or a refusal, on a number change shortly after an email change (suggest 7 days, a proposal), because an attacker who has taken the email can then add a number.
   - Pins in `auth_config.test.mjs` for the keys above.
6. A Send SMS hook function only if a pre-send country signal or a second provider is wanted; otherwise use the native provider (fewer places that see the number).
7. Test numbers (`auth.sms.test_otp`) in local config only, never in hosted staging or production; a pin on the production config that the key is absent. Provider secrets only as `env()` references.
8. A Send SMS hook never logs its payload, not even on error (phone and code are in it).
9. Verified phone is never used for recovery, step-up or sign-in (SIM swap and number recycling make it a weak proof). A person who inherits a recycled number that is on another account has a release path through support (identity checked by email, then the number is removed from the old account); it is a support-led act, never automatic. Owner (BL-1943 item 2), PROPOSED: the support lead (handle `support`) owns each release case end to end, because the request reaches support first and one named person must answer for the identity check; ops runs the removal after the support lead records the check, through a database procedure that is to be built (no support console or admin tool for this exists in the repo today), and security reviews the runbook and the log line (the case id only, never the number). Proof of identity is the email of the account that holds the number, answered from that inbox; the new holder's word alone is never enough (they only hold the number). Before removal the old account's email is told, with no number in the message, and a hold gives the real owner time to object: floor 72 hours, a proposal for the exec team and not a fact; support may lengthen it, never shorten it. If the old account's email is dead (bounces, or the person cannot open it), identity cannot be proved by that inbox: the case waits out a longer hold (floor 14 days, a proposal) with notices to the address on file, and the old account's other sign-in methods (Apple or Google) are used as proof if the person can sign in with one. Removal clears both `auth.users.phone` and the phone row in `auth.identities`, since an existing phone identity is a second place the number lives (name from `verify.go` lines 426 to 450; the cleanup path was not read [UNVERIFIED]). The removal is written to the audit trail (an auditable table, not only the support log), as the case id and the actor. The reason for one owner: a path every team may use is a path no team keeps. Nothing here is built; the runbook and the SLA are for support to write.
10. NS-54-R23 versus R18. Read, `user.go` lines 142 to 147: `UserUpdate` for a phone that differs from the user's own checks `models.IsDuplicatedPhone` and returns 422 `phone_exists` before any text is sent. So native Auth answers "already registered" at Send, faster and with different words than for an unregistered number, and cannot meet R23 (same screen, same response, same timing, a text for either). To meet it we would need a gateway or edge function in front of `PUT /user` that returns one neutral response for both cases and makes the same vendor-side delay, plus an actual text to a registered number (which still costs a text, so the spend cap counts it). That is a new component. Until it exists, R23 fails natively and the phone step stays off. R18 is about a method linked to another account. Three cases, so the two do not pull against each other: (1) Send: one neutral screen, same response, timing and spend, whatever the number; (2) Verify, when the code is right but the number belongs to another account: a refusal in words that says the number cannot be added and names nothing about the other account; (3) the person signed in to the account that already holds the number: the duplicate hint is allowed there. Product decides; test with test numbers.
   Proposed card line for NS-54 section "Conflicts" (BL-1943 item 5; draft text only, no requirement is changed): "Conflict: NS-54-R18 refuses a method already linked to another account with words, and NS-54-R23 says Send shows the same screen whether or not the number has an account. Native Auth refuses a duplicate phone before any send (422 `phone_exists`, `user.go` lines 142 to 147), so it cannot meet R23 on its own. Proposed reading, for product to decide, in three cases: at Send, R23 governs (one neutral screen; the response, its timing and whether a text goes out are identical for a registered and an unregistered number, and a text to a registered number still costs a text); at Verify, R18 governs (the words say the number cannot be added and name nothing about the other account); a person signed in to the account that holds the number may see the duplicate hint."
