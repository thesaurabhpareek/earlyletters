## 3. How every alert is built (rules for `sync`)

1. **Fixed subject per kind.** The subject is a content key with no variable except nothing: no address, no name, no device, no time. Example family: "A change to your sign-in", "Your book was opened on a new device". The preheader follows the same rule. (L4 never in a subject, `DATA_CLASSIFICATION.md:69`; `packages/emails/README.md` preheader rule.)
2. **The body may carry** the event time in words with the zone short name (account time zone, else last synced device zone, else US Pacific), a device class word, and the help route. Nothing else personal. No IP, no place. A place invites a wrong "that is not me" panic and is a location datum we do not hold.
3. **No action link that signs anyone in or changes anything.** An alert never contains a one-time token, a magic link or a "yes it was me" link: mail scanners prefetch links and an attacker can forward the mail (`SECURITY.md` section 3.1). The only links are Help (the support mailbox) and instructions to open the app. Rec; the CISO reads it (Q-COM-4 council). D1 keeps it: no action link at v1; the Stop page of F02-REQ-017 waits for recording backup (CPO and CDesO council returns), and the email carries the in-app path in words.
4. **Enumeration safe.** Alerts go only to the inbox owner. No screen or reply says whether an address has an account (`auth.en.ts` header rule; `SECURITY.md` 3.6).
5. **Sent from an Edge Function with the service role inside the function**, rendered by `renderForResend` from `packages/emails/generated/resend.ts`, with Resend's `Idempotency-Key` header set from the key in the table (`packages/emails/README.md:20-32`). The service key and the Resend key live only in the function's secrets (never the app). The function logs the kind, the request id and the outcome; never the address, the device hash, the time of the person, or the body (rule `DATA_CLASSIFICATION.md:69`).
6. **Rate limit and abuse (D2).** No A2 email exists in 1.0, so no cap is built or tested for it. Alert mail follows the PRD V2 summary rule (F02-REQ-017, `docs/prd/v2/features/F02-account.md:232`): the first 5 alert mails per account in an hour send one by one; later ones fold into one summary sent within minutes, never held to the next day, so a flood cannot hide the one real warning. A backstop of 20 alert mails per account per day applies on top [E: the reviewer's number; no card, ruling or law sets it; product confirms]. A4 receipts and A5 are never folded [E]. The 20 a day backstop counts only alert mails that are not required notices: required notices (A4 receipts; `CATALOG.md:135`) and the security alerts A1, A3 to A9 are never held by it [E, product confirms]. The earlier text gave A2 two caps that disagreed (1 per 24 h in the table, 5 in this rule); both are removed (D2). Each alert is also limited by its own idempotency key (one per event). The hourly fold and the daily backstop are what stop alerts being used to bomb an inbox.
7. **Auth check.** The function is not callable by a client. It reads a database event or a queue row written by a security-definer function; the caller is the database role or a scheduled job (as `purge-worker`). No public endpoint sends an alert.
8. **Quiet hours.** Alerts are exempt from the 21:30 to 07:00 hold (a takeover warning sent 8 hours late is worse), as sign-in mail already is (`CATALOG.md:137`). AGREED (D2); Q-COM-3 is closed.
9. **Delivery failure.** A bounce on an alert shows I7 in Me, Account. Apple Hide My Email: the same registration rule as sign-in mail (`CATALOG.md:141-150`).
10. **Both channels agree.** Where an in-app line exists (I5, I6, I8) it states the same facts as the email; the email is never the only place a legal fact appears.
11. **One calm shape (CDesO).** Every alert uses one template: a fixed subject; one sentence of what happened with the time in plain words and the zone; one sentence of what to do; one line of help. Plain text and HTML carry the same words; type at least 16 px equivalent; no colour carries meaning; no image, no tracking. Words stay PROPOSED.

## 4. Data path per alert (what reads what)

| Step | Reader | Data | Path |
|---|---|---|---|
| Detect | Supabase Auth hook or a database trigger | session start, device hash | Inside the database; no client call |
| Decide | Edge Function with the service role | Account id, kind, last sent time | Function secrets; RPC with `SECURITY DEFINER` and a pinned search path (`data-architect` writes it) |
| Render | The function | Fixed content keys, event time, device class | `generated/resend.ts` |
| Send | Resend | Address (L3), subject, body | HTTPS; Resend stores content by default (`CATALOG.md:22` E-1), which is why no L4 is ever in the body |
| Record | Database | Alert kind, account id, time, key (L3 and L2) | A row in `ops.audit_log` or an alert table; no body text |

## 5. Gaps and risks found

1. No card, no sender and no trigger for A1, A3 and A6 although the catalogue plans A1 at 1.0 [V]. A thief with the inbox gets no warning today. D1 (founder approved 20 Nov; product confirms) sets the order: A1 before the first outside family, A3 and A6 after the BL-598 runbook.
2. The server side of "repeated failed codes" is unverified: no per-address lockout is documented and the founder-paging job is not in the repo [U]. The pause on the phone is advisory only: it lives in memory and is lost on restart (`pending.ts:72`).
3. The parent control "Sign out other devices" exists but sends no email and the other phones learn only when their session next refreshes [E: vendor behaviour not read]; it does not end sign-in by email, so it is not a recovery from a stolen inbox. The founder-side levers are NOT RUN (`sign-everyone-out.md:3`).
4. The recovery runbook named by BL-598 is missing, so A3 has no trigger and hand recovery has no written rule (`back-office.md:92`); D1 (founder approved 20 Nov; product confirms) holds A3 and A6 for it (`docs/BACKLOG.md:2783`).
5. Auth template placeholder header still says `{expiresIn}` "1 hour" (`auth.en.ts:18`) while the setting is 15 minutes (`config.toml:74`); a stale comment, but a template test should assert 15 minutes appears [E: low risk].
6. The built `new-device-sign-in` template tells the parent to reply "Not me" and says "We will sign that device out" (`packages/content/src/emails/auth.en.ts:190-199`); no lever signs a device out on a reply [V, C10]. Build the lever or remove the line (C10, PROPOSED). With D1 the A1 words carry the in-app path instead of a reply, so the line is replaced, not kept. Not to be confused with `features/auth.en.ts`, which holds the control label (`:291`).
