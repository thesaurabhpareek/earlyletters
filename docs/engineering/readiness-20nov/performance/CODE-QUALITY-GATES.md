## 4. How reviewers apply them

1. **A red gate is never waived in a PR.** A test is fixed, not skipped (CODE-R03). The only written exceptions are `Size exception:` (CODE-R02), `Size-change:` (size gate), and a licence exception entry; each names an owner and is a founder decision when it breaks a founder budget (40 MB).
2. **Which lens reads what** (my reading of the chapter owners in `docs/engineering/README.md`; the steward confirms): `principal-architect` reads G2, G4 to G7 and size; `compliance-engineer` reads G11, G12, G15; `data-steward` reads anything touching `supabase/**`; `security-architect` reads the media and network scans; `qa` reads G3, G9 and the device rows. A reviewer looks at the diff of a baseline file first, because a baseline that grew is a gate that was loosened.
3. **Baselines only shrink.** `tsc-baseline.txt`, `file-size-baseline.json`, `size-baseline.json` change in the same PR as the code that moves them, with the reason in the body. A PR that raises one needs a second reader and the founder's acceptance if it raises the size baseline.
4. **Constitution first.** Before style, a reviewer asks the four questions of CLAUDE.md: does any machine edit bypass `verifyEdits`; does anything write, rewrite or shape a person's words; does any text, audio, name or picture reach a log, analytics or a crash report; is real family data anywhere. The gates above only support these; none replaces them.
5. **Agents.** An agent runs `npm test` and `npx tsc --noEmit` in `apps/mobile` before opening a PR and says which known baseline failures it saw (9 test files, 5 `tsc` errors in the sandbox). A new check is added in its own PR (one concern), with a test that fails on the old code.
6. **Where a gate does not exist yet,** the reviewer applies the rule by reading and writes `unenforced: G<n>` in the review so the gap is counted. The steward updates `docs/engineering/ENFORCEMENT.md` when a gate lands (its totals are stale: "192 rules, 42 enforced" is a 3 Oct count [V], and its own header says so).
