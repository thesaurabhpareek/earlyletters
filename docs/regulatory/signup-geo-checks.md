## 3. Design of a lightweight geo block (recommendation, nothing decided)

3.1 Where it runs. Keep the existing Supabase `before user created` Postgres hook (`public.hook_before_user_created`). Reasons: it is already built and tested; it runs for every way an account is created (email, Apple, Google, a phone later) so no path can skip it; the app cannot bypass a server check. An Edge Function in front would add a second place to maintain and would not see the creation event. The web contribution page (D-055, later) needs its own check in its own server code and records through `ops_count_check` (`20261121030000_compliance_gates.sql:296-304`).

3.2 Signal. The request IP given in the hook input (`metadata.ip_address`, F11), turned into a country by the monthly DB-IP table inside the database. No platform country header is verified (F13), so do not design around one. Whether the `ip_address` Supabase passes is the client's real address behind its proxies is not stated on the page read: add it to the local or hosted test (a sign-in from a known network records `pass`, APPLY.md File 39 step 3).

3.3 What we store or log. Nothing identifying. The IP exists in memory in the function only; the stored result is one daily counter by outcome (`pass`, `block`, `geo_unknown`, `geo_stale`, `error`) with the country code on `block` rows only. No new data class (the counts are L2 per the column comments `:222-226`), no table holds an IP. Open: Supabase Auth's own audit log may keep the IP; until its retention is read from Supabase, the Privacy Policy line "we do not keep the IP" is true of our tables only. The App Store privacy label question (does using an IP in memory for a decision change "Identifiers" or "Location") is COUNSEL_PACKET Q57 via CPrivO-2; engineering reading: used in memory, not stored and not linked, so no new collected type, counsel must confirm. Nothing about the person is logged on a refusal: the message is a fixed string, and the hook does not log the error text (`:275`).

3.4 Failure mode. Recommend keep fail open: no IP, unknown country, stale file, lock during a load, or error lets the person in and is counted. Reasoning: a blocked-by-mistake adult who is outside the list is a lost family; a late monthly file would otherwise stop every sign-up; the Terms 2.4 attestation and US-only storefront remain the second layer; the counts plus an alert make a silent failure visible. The risk of fail open is a determined person with no resolvable IP; the founder asked for a lightweight check. Counsel must confirm that fail open is acceptable for a free service; if counsel says fail closed for `geo_unknown`, that is a founder decision, and a monitored allow-list is the way to keep honest users in.

3.5 VPN and other limits, stated plainly. A VPN, a proxy or mobile roaming gives an IP in another country, so a person in a blocked place can pass, and a traveller on a blocked-country network can be refused. The country table is wrong for some addresses (a vendor's own accuracy limits; the repo notes this in `references/sanctions.md` known limits). Region level places cannot be resolved from country data. A refused person can write to support; support never asks where they are. This is a risk-based programme, not a guarantee (F4 is [UNVERIFIED] this session).

3.6 User-facing message. Reuse the existing PROPOSED words, which already pass the content rules and the voice guide (no reason, no place named, no blame, no "us"): title "{app} can't be set up from here." and body "If you think this is wrong, get in touch." with the Terms link and Get in touch as the two quiet actions (`packages/content/src/features/auth.en.ts:204-209`). Keep them held for counsel as marked in the file. Add the DB-IP attribution link (https://db-ip.com) in Settings, Licenses (BL-553). For the provider path the one-line inline message already exists (`region_refused`, `auth.en.ts:244`); the gap is proof that it shows (GEO-2), not new words. No changes to the strings are made by this document.

3.7 Age and 18+ alignment. Order: the device gate runs first and stores one boolean; the hook runs at user creation and knows no age; the Terms step records `age_attested` after. Keep that order (a geo refusal then happens before any age data exists on the server). Under-18 answers create nothing server-side. For a state store-signal duty, the Declared Age Range work stays on its own row (`age-assurance.md`). The geo block and the age gate share nothing and must stay separate: never use country to infer age.

3.8 Country-code list for a phone or country picker. Today there is no picker (section 1). If a phone number is added (section 6), the list of country calling codes shown must be generated from the same data as the block list (`ops.restricted_jurisdictions` where `scope = 'country'` and `status = 'block'`), by a build step, so the two cannot drift, and the picker must hide those codes. The dial code for each blocked country is not listed in this file because no source for them was read this session: [UNVERIFIED], take them from an ITU or library data source and have the test compare the generated hidden list to the jurisdiction table. Also needed: reject server-side a number whose code is on the list even if the app was edited. Hiding a code in a picker is a convenience; the server check is the control.

3.9 People who already have an account. The hook fires on creation only. Options for counsel to weigh: (a) leave as is, and rely on Terms 2.4; (b) a sign-in-time check. Whether Supabase offers a hook at sign-in that could carry it was not read this session: [UNVERIFIED]. Recommend (a) for now and ask counsel (item d in section 2).

## 4. Social login recommendation (Apple first)

What the repo has now:
- Sign-in sheet order: Apple, then Google, then "Continue with email", passkey link only when enabled (`apps/mobile/src/app/(auth)/sign-in/index.tsx:1-5`, `:128-130`). Code for both providers exists (`apps/mobile/src/lib/auth/apple.ts:43`, `google.ts:38-51`, the nonce flow in `apple.ts`). Google shows only when both client ids are configured and the platform is iOS (`google.ts:38-40`).
- Local config has both providers disabled (`supabase/config.toml:144-152`); the hosted state is in `docs/ops/AUTH_SETTINGS.md` and is a console and secrets step (`docs/ops/AUTH_SETUP.md` sections 2 and 3), not read as live here.
- Email link or code with confirmation required (`supabase/config.toml:67`; AUTH_SETUP section 1). Account deletion in the app (`apps/mobile/src/app/settings/delete-account.tsx`) and Apple token revocation (AUTH_SETUP 2.7; `apple-token` function).

What Guideline 4.8 requires if we offer Google beside Apple (F5): Google Sign-In is a named third-party login, so the app must also offer an equivalent login service that limits data to name and email, lets the person keep the email private, and does not track interactions for advertising without consent. Engineering reading: Sign in with Apple is the usual way to meet that; the guideline text read does not name Apple as the answer, so the Review Notes should say how each of the three features is met. The email-link path is our own system, but the "exclusively your own sign-in systems" exemption no longer applies once Google is offered. Counsel must confirm; App Review decides. Terms 3.1 (`docs/legal/terms-of-service.md:48`) lists only Apple and an email link and code as sign-in ways, so offering Google also needs Terms, Privacy Policy and subprocessor (`docs/legal/subprocessors.md`) updates, which are legal text for counsel. Apple alone, or Apple plus email, needs no 4.8 line. Google Play (F10) is secondary only and Android is not v1.0.

Effort and risk of leaning on social login:
- Effort: small for code, because it exists. The work is console and secrets (Apple key, services id, Google clients), which are physical acts, plus tests of the provider path against the hook (section 1 item 4) and the refusal screen for provider errors.
- Benefits: no email-code hop, fewer lost sign-ins, and the provider has already verified an email (Apple always; Google marks email verified: [UNVERIFIED] here, nothing read).
- Risks: Apple Hide My Email gives a relay address, so our email to that person works only after the relay domain setup (AUTH_SETUP 2.5), and we must not treat an address as a proof of location, age or identity; a name or email from a provider is a new input to the clean-name rule (the name is shown first time only and kept in the Keychain, AUTH_SETUP 2.6). Account deletion must revoke Apple's token (F6; built) and must also work for a Google-created account; Google token revocation was not checked in this session. A provider login does not carry any country or age, so it does not replace the IP check or the age gate. The Apple account country and the Google account country are not signals we use (none read).
- What changes for validation: email verification is by the provider, so `enable_confirmations` does not run for them (the repo's own flows were not re-tested here); duplicate accounts by one person with two providers depend on `enable_manual_linking = false` (`config.toml:48`) and need a test; the hook must be tested for the `signInWithIdToken` path, since the hook documentation read only says "before user created" (F11) and does not name provider sign-ins [UNVERIFIED].

Recommendation (not a decision): keep Apple first; offer Google only together with Apple (already so) and with a Review Notes line for 4.8; keep email as the third way; turn nothing on that a test has not shown to pass the hook. A test must show that no social token is stored off the device, except Apple's refresh token held wrapped for revocation as built (F6: the app "may not store credentials or tokens to social networks off of the device"; whether Apple's own token is covered by that line is a counsel question). Do not remove email: a person without either account must not be locked out, and 5.1.1(v) asks that required personal information be limited to what is needed (F6).

## 6. If a verified phone number (SMS one-time code) is added (recommendation, nothing decided)

The founder said he would prefer a verified phone number for everyone, in future and even today. A product manager writes the requirements and scenarios in a separate card; this section is only how it changes the validation. It is not a decision; counsel must confirm each reading.

What it would change today: the repo promises no phone number is collected (`docs/legal/DATA_CLASSIFICATION.md:563`, LEGAL-REQ-012; `supabase/config.toml:125`), and D-137 decides only "no name screening", on data-minimisation grounds. A phone number for every account would reverse the LEGAL-REQ-012 "never collected" description and weaken the minimisation reasoning behind D-137 without reversing D-137 itself. Either way it is a change to what a user is promised and needs a founder decision plus counsel on the Privacy Policy and Terms (skill section 3, step 3) before any build.

The country code as an embargo signal, with limits:
- It names the country that issued the number (the numbering plan), not where the person is (F14). A person in a blocked place can hold a number issued elsewhere, and a person from a blocked country who lives in the US keeps their issuing code: the code over-blocks and under-blocks (the second needs the first reading of F14; roaming is covered by the same "issuance, not location" point).
- VoIP numbers are a weaker identity signal (F14, a vendor claim). Number portability: no source read, [UNVERIFIED]. The effect of virtual or temporary numbers, and carrier lookups that say a number's current network: [UNVERIFIED], no source read.
- So the phone code is a second soft signal beside the IP check, not a replacement. It also helps for the US-only storefront reasoning only as support, which counsel must confirm.

What the geo block would check at which step:
1. The device age gate (unchanged).
2. Number entry: hide the calling codes of blocked jurisdictions in the picker (3.8) so an honest person is not offered one; this is convenience.
3. Before an SMS is sent: a server check that the number's code is not on the blocked list, so no SMS goes to a blocked-country number (this also avoids the SMS fee, F15). Whether Supabase has a hook before sending was not read: [UNVERIFIED]; an Edge Function in front of the send call is the alternative.
4. User creation: the existing IP hook (unchanged). Both signals are checked; either one refuses; a mismatch between them is only counted as a content-free outcome, never stored per person.
5. Terms plus age confirmation (unchanged).

What personal data a phone number adds:
- A new L3 field in `auth.users`, from L3 convention at `DATA_CLASSIFICATION.md:563`; needs a column row, a retention line (kept while the account exists, deleted with it; the deletion spec `docs/legal/DELETION_AND_EXPORT_SPEC.md` must erase it and the SMS provider's copy), and an export entry.
- The App Store privacy label gains a collected contact data type for the phone number (the category name was not re-read this session, [UNVERIFIED]); `docs/legal/app-store-privacy-labels.md` row 46 is the place to change; the Privacy Policy must say it.
- A new subprocessor, the SMS provider (F15), in `docs/legal/subprocessors.md`; the number crosses to them for each code.
- Logs: no phone number in any log, analytics event or crash report, including the hook, rate-limit logs and the SMS provider's dashboard retention (check it; unread). Counts stay content-free.
- Costs and abuse: SMS cost and "pumping" fraud need rate limits and a CAPTCHA (F15); that is an ops and security row, not this file's.

Which rules it does and does not help with:
- Sanctions: it adds a soft signal at sign-up, and it is not a screen of persons (no name or list screening; D-137 stands). It does not catch a VPN user with a non-blocked number, and may wrongly refuse a person with a blocked-country number who lives elsewhere (the Terms 2.4 attestation and a support route stay). Counsel must confirm that it is worth the new identifier.
- Age: it does not prove age (a number is not an adult's identity; no source read says otherwise, [UNVERIFIED]); the 18+ gate and the Terms attestation stay the controls. It helps one thing: a stable identifier for repeat attempts, which would itself be a new data use needing counsel.
- Apple 4.8 (F5): a phone login the app runs itself is "your company's own" system; as long as Google is offered, the Apple equivalent is still needed. A phone number is not a way to meet 4.8.
- Apple 5.1.1(v) (F6): requiring a phone for everyone conflicts with "Apps may not require users to enter personal information to function, except when directly relevant to the core functionality of the app or required by law." Counsel and the CCO must read that against the founder's preference before it is built. Offering a phone as optional, or only on a step-up, is the lower-risk path to put in front of counsel. This is a reviewer-risk note, not a ruling.
- Cost to the user in the family flow: a second person invited by link would also need a phone; that belongs in the product card.
