# PR #602 (BL-594): founder read, 8 Nov 2026

Prepared by the security engineer for the founder's own read. This is a preparation, not a decision and not a review. PR head at time of writing: 50344809. Credentials path (CR-47), so the merge needs your read or two counted reviews.

## What the PR changes, in plain words
Our Edge Functions used to read only the old Supabase keys. Supabase is retiring those by the end of 2026, and the audit item AF-06 says to switch them off on staging. If we did that today, invite codes and the Apple token capture would stop working. This PR adds one small file that picks the new key if it exists and the old one if not, and sends the key the way Supabase says each kind must be sent: a new key on the `apikey` header only, an old key on both headers as before. Five functions use it: invite-redeem, apple-token, analytics-forget, subscription-status and the purge worker. Nothing changes while only the old keys are set.

## Five things to look at in the diff
1. `supabase/functions/_shared/keys/keys.ts` lines 31 and 36 (`secretKeyOf`, `publishableKeyOf`): the new key wins over the old one. Check that you are happy for a new key, once present, to be used silently, and that a malformed dictionary falls back to the old key rather than failing (lines 14 to 24).
2. `keys.ts` lines 41 to 50 (`isJwtKey`, `serviceHeaders`): the decision about the `Authorization` header rests on a regex. A new `sb_secret_` key never goes out as a bearer token. A string that looks like three dotted parts is treated as an old JWT key. Check the regex cannot be fooled by a real new key shape.
3. `supabase/functions/invite-redeem/handler.ts` lines 105, 106, 147: the one call that carries the service key for a person-facing route. Confirm the person's own call (the session check) still uses the publishable key plus their own token, and only the redeem RPC uses the secret key.
4. `supabase/functions/apple-token/handler.ts` lines 104, 122, 356: `readAppleTokenConfig` still returns null when there is no secret key (the "refuses as not configured" path), and the token store call is the only service-key call. The anon key is now allowed to be absent (`publishableKeyOf` returns null), as before.
5. `supabase/functions/purge-worker/config.ts` lines 50 and 75 and `lib/service.ts` line 108: the purge worker deletes accounts and storage. The "missing" check now accepts the new key under the old name `SUPABASE_SERVICE_ROLE_KEY`, and every call (database, storage, auth admin) now goes through `serviceHeaders`. This is the highest-impact caller.

## Threat it closes (STRIDE headline)
Availability and Elevation of privilege on key rotation. Without this PR we cannot retire the old, long-lived, non-revocable-per-key JWT service key, which is the most powerful secret in the system (it bypasses row-level security). With it, the project can move to revocable `sb_secret_` keys and switch the old ones off. It does not add a new exposure: no key is logged or returned, and the new key is never placed in a bearer header.

## What could go wrong, and the way back
- PostgREST, Storage or Auth admin may reject a new secret key sent on `apikey` alone. Effect: purge worker, invite redeem and Apple capture fail with 5xx on staging. Way back: do not deactivate the old keys until staging proves it (CR-47); while both are set, remove `SUPABASE_SECRET_KEYS` from the function secrets and the code falls back to the old key at once, or revert the PR.
- A project has both sets and the new key is wrong or restricted: the new one wins and the function fails although the old one would work. Way back: the same, unset the dictionary.
- Anything outside these five functions that still reads the old names: `scripts/ops/verify-deletion.ts`, `restore-drill.ts`, `enumerate-affected.ts` and `scripts/ops/lib/target.ts` read `SUPABASE_SERVICE_ROLE_KEY` only. They will break when the old keys are switched off. This PR does not cover them; worth a backlog item for `product`.
