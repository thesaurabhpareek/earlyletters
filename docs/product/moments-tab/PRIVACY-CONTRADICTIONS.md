## The rule: these ship together

The hybrid design adds the picker door (F1, stores a stripped copy of a picked picture on the phone) and the library read (F2, reads date, time and place on the phone). Two review findings say the paperwork may not lag the behaviour:

- **EX-CLO-1 (BLOCKER, CLO role):** the Privacy Policy build list says the first App Store build has servers off; the label and `apps/mobile/eas.json` say the first store build is the `production` profile with servers on.
- **EXH-PRV-1 (BLOCKER, privacy role):** the door attaches stored copies, so policy, label and the backup line "must match in the same build". Until then the door stays out of any store profile; it may stay in `development`, `preview` and `testflight`.

So rows C-1 to C-9 below are one change set, not nine. They merge together, in the same build as the behaviour (spec R81, R240, R266), as drafts for counsel: Privacy Policy 3.1.0, Terms 4.2.0, in-app disclosures 3.5.0, App Privacy label 2.3.0, each versioned per `docs/legal/POLICY_VERSIONING.md`. Publishing any one without the others leaves a public statement that the shipped build contradicts. Whether the resulting texts are accurate is for counsel: counsel must confirm.

What is in each profile today (`apps/mobile/eas.json`): `development`, `e2e`, `testflight` have `EXPO_PUBLIC_SERVER_FEATURES` off; `preview` and `production` have it on; `EXPO_PUBLIC_BACKUP` is off everywhere; no profile sets `EXPO_PUBLIC_PHOTOS`. The photo UI is therefore not in any build today, and these contradictions are about the build the hybrid would ship, not the build that exists.
