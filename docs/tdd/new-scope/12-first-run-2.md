### 4.2 What is built (Fact [V])
- One door, two ways in: `welcome-sign-in.tsx`; enumeration safety (`shouldCreateUser: true`, `email.ts:35-37`); PKCE link bound to the asking phone, refusal while signed in, claim after consent and a tap (`email.ts` header; ADR 0023; `account-claim.logic.ts`).
- Code length is a build constant: `EMAIL_CODE_LENGTH` reads `EXPO_PUBLIC_EMAIL_OTP_LENGTH`, 6 to 10, default 6 (`email.ts:28-29`); no `eas.json` profile sets it (`grep -c` returns 0). Server `otp_length = 6` (`config.toml:71`), pinned by `supabase/tests/auth_config.test.mjs:73-75`.
- Pending-link note lives one hour (`email-link.logic.ts:36`) against a 900 s token (`config.toml:74`). The wrong-code pause is a per-process `Map` (`pending.ts:72`).
- Email is trimmed (`email.ts:36, 43`); lower-casing exists only for the wait key (`errors.logic.ts:117-119`). Apple requests full name and email (`apple.ts:51`); the name is held in the Keychain until the Terms step writes `profiles.display_name` (`apple.ts:63`, `consent.ts:140`), and no screen shows it.
- Apple revocation: one `getCredentialStateAsync` read when a signed-in user id first appears (`session-provider.tsx:270-281`, `apple.ts:81-91`). Correction to round 1: `expo-apple-authentication` 57.0.2 does export `addRevokeListener(listener)` (`build/AppleAuthentication.d.ts:70`, `.js:128`), and its Swift module posts it from `ASAuthorizationAppleIDProvider.credentialRevokedNotification` (`ios/AppleAuthenticationModule.swift:87-103`) [V: read in `node_modules`]. My first grep matched "Revoked" and the export is spelled "Revoke". No native work is needed.
- Send and Continue are disabled silently: `email.tsx:69` `disabled={value.length === 0}`, `code.tsx:225` `disabled={code.length !== EMAIL_CODE_LENGTH || ...}`.
- The outage screen has two actions only: Try again and Start on this phone (`outage-screen.tsx:30-39`). `email_wait` and `rate_limited` are outage errors (`gate.logic.ts:164`). NS-41-R12 wants Sign in with Apple reachable there: **gap [V]**.
- Wording defects: `noEmailHelp` (`strings.en.ts:1503`) and `emptyBookHelp` (`:1504`) name Google; the sign-in privacy line and `authCopy.consent.terms.body` (`auth.en.ts:232`) say "the people you invite" (CG3).
- Second account: claim and upload are blocked (`sync/ownership.ts:49`), display is not; BL-961 part 1 `bookVisibleTo` merged (#869); parts 2 and 3 open (#871, #879).

### 4.3 Design

**FS-15 One normalizer and reasons in words (R8, R24).**

Empty email or short code sets a `reason` state (`email.reason-empty`, `code.reason-short`, the E-S05 and E-S06 states in `EXPERIENCE-ACCEPTANCE-2.md:78-79`), announces it, and moves focus to the field. PROPOSED keys `authCopy.email.needEmail` ("Type your email to continue.") and `authCopy.code.digits` with `{n}` (replaces `sixDigits`). `content` writes them (BL-965); screens read `EMAIL_CODE_LENGTH` for `{n}`.
- First-run `email_wait` and `rate_limited` on Send: the outage screen gains one quiet action that opens Sign in with Apple when `AppleAuthentication.isAvailableAsync()` is true (R12, R21). It reuses Apple's own button and no new words. The Welcome's footer already holds the button; the action returns to it. Mutant: remove the action.

**FS-16 `killSwitches.signIn` (R25; CL-111, ADR 0029 key list; owner `sync`, PR FP-5).**
- Contract: add `'signIn'` to `KILL_SWITCH_KEYS` (`packages/api/src/kill-switches.ts:10-35`) and `signIn: bool(false)` to `KillSwitchesSchema` (`remote-config.ts:67-79`), so an older signed config without it parses off (the M14 rule, `kill-switches.ts:39`). Hide only; fail-open (a stale config keeps an earlier `true`, `withFreshKillSwitches`, `remote-config.ts:179-183`).
- Phone reading: `isKilled(config, 'signIn')` in the first-run route, not `mayRun` (which needs a build flag, `capabilities.ts:266`). The route returns the E-S14.outage view with the local start for a person with no session; it is never read for a session that already exists, so a signed-in phone is untouched (R25). A test feeds a validly signed hostile `signIn: true` to a phone with a session and asserts the session is kept and refreshed as before (FR-SEC-16, `risk-security.md:130`).
- Server side: no function reads it (`supabase/functions/_shared` has `parseKillSwitchList`; sign-in is Supabase Auth, not our function). Flipping it removes the Welcome's buttons, nothing on the server. Contract-drift test (`packages/api/test/contract-drift.test.ts`) gets the key.
- Word for E-S14.killswitch: existing `system.offline.*`/`unreachable` family (`EXPERIENCE-ACCEPTANCE-2.md:87`); no new key.

**FS-17 The wrong-code pause survives a kill (R9).** Rec: when the fifth wrong code in 15 minutes occurs, `pending.ts` writes one time value to Keychain `scribe.auth.codePausedUntil` (this device only, no address, no count). On launch and on the code screen it is read; a value in the past is deleted. Send a new email neither clears nor shortens it. The in-memory map keeps counting per address. Trade-off (OQ-F5): the Keychain value is phone-wide, so a different address is also paused for up to 15 minutes; storing a hash of the address would be L3-derived data on the phone, which the card forbids (section 11, "never on the phone"). The server's per-IP verify limit is the real control (setting 4 below).

### 5.2 The consent builder, and why it lands first (FS-21)
- Fact [V] `20261108000000_consent_record_fields.sql` (pending apply [U]) adds `app_build` and `os_major` and a BEFORE INSERT trigger: a sheet act (`signin_sheet`, `consent_sheet`, `reconsent_sheet`) with `rendered_sha256` or `locale` null raises 23502 when the row carries `app_build` (`:75-78`) or the database setting `app.consent_fields_required` is `on` (`:77`). So there are two ways to be refused: send `app_build` without the hash, or have the server setting turn on while an old build is in the field.
- Fact [V] The phone sends none of the new fields and a constant locale (`consent.ts:124` `p_locale: 'en'`); the call has no hash, build or OS parameter (`:115-127`). The card cites `:113` for the constant; it has moved to `:124` [V].
- Rec FS-21 One builder: `lib/auth/consent-record.ts` exports `buildConsentAct({document, version, action, method, surface, shownText, locale})` returning the RPC argument object: `p_rendered_sha256` (hash of `shownText` exactly as drawn, from `lib/sha256.ts`), `p_locale` (the language of the text shown), `p_app_build` (EAS build number from `Constants`), `p_os_major` (`Platform.Version` major only), plus the existing fields. `consent.ts` calls it for every act; a contract test (embedded Postgres, `npm run test:db` shape) runs the builder output against `record_policy_act` and the trigger, with a hostile case (null hash) that must raise 23502. No `age_signal` (CF-1).
- Hash source: BL-577 asks the hash to equal "the bundled manifest hash for that version and locale". Rec: a build-time manifest `packages/content/generated/consent-manifest.json` (document, version, locale, sha256 of each consent sentence) produced by a script and checked in a content test; the builder hashes the drawn string and a test asserts equality with the manifest. Owner `content` for the script, `mobile` for the builder.
- Order (corrected in round 2; the first version was unsafe). The migration goes FIRST: `20261108000000` drops the old 11-argument `record_policy_act` and creates one with `p_app_build` and `p_os_major` appended and optional (migration header lines 23-25; `supabase/APPLY.md:1187-1199` File 29: "Today's app records exactly as before", check query `pg_get_function_identity_arguments`). A builder that sends `p_app_build` to the old function would find no candidate and fail every consent, so: (1) the founder applies the migration with the app's current build still in the field (backward compatible: named arguments still resolve); (2) the builder (FP-2) ships; (3) a measured gate, not a hope: before `app.consent_fields_required` is set to `on`, `ops` runs the read-only count of sheet acts in the last 14 days where `app_build` is null (a query on `policy_acceptances` by the service role, no content) and the setting waits until it is zero for 14 days; (4) only then the founder sets the setting. An "update line" cannot protect step 4: a build older than the reader has no reader, and the reader needs `minSupportedVersion` set by a founder step anyway, so FS-33 is a courtesy and no longer part of this order. Signature probe (FS-21b): one `supabase/tests` case calls `record_policy_act` by name with the 11 old named arguments and with the 13 new ones, both succeed before the setting is on; a second case with the setting on refuses the 11-argument call (23502). The probe is also a `scripts/ops` staging check the founder runs once after step 1. Risk RK-3 stands as the irreversible-in-effect step; its guard is now the measured zero.
- Idempotency (R8): built on develop: `consent.ts:88` `heldAnswers(idempotencyKey)` (`consent-key.logic.ts`) holds one key and one client time per answer. Our earlier designs (`08-keeping.md:123`, `privacy.md:100`) cite `consent.ts:117` as minting a key per call; that cite is stale [V]. R8 needs only the title (`[NS-42-R8] one row after a retry`) and a mutant (mint a new key per call).
