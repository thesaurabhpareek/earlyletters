**Row shape (NS-46-R1).** `{ id, layer, nameKey, tone, publicTitleOk, preTicked: false, precision, countries?, tradition?, rule }` with `rule` one of: `fixed {month, day}`; `nthWeekday {month, weekday, n}`; `easter {offsetDays}` (computus, about 30 lines, LD-18); `astronomical {event, instants: {year: utcIso}}`; `table {rows: [{year, date | 'n/r', authority}]}`. `layer` is one of seasonal, family, civic, tradition, cultureLed, national. - `upcoming(ticked, today, horizonDays, ctx)` returns `[{ dayId, date }]` sorted, with moves applied; used only by the planner.

**Oracle tests (NS-46-R11, R12, R24; LD-18).** `packages/content/test/days.calendar.test.ts`: rule dates 2026 to 2030 against a committed oracle table with `authority` and `readOn` per row; the test fails if an oracle row has none (as `helplines.test.ts` does, `21:273`). ## 4. The days store (NS-47 storage rows)

### 4.1 Class and place
- Class L4 for the whole file (NS-47-R1: highest class in it wins). One registry row in `docs/legal/DATA_CLASSIFICATION.md` section 4.6 (founder-merged; privacy owns, K-9 in SECQ). The in-memory browse filter (tradition, country) is component state only (NS-47-R2).
- File: `<Application Support>/days/days.v1.json`. **Fact** The app already derives Application Support from `Paths.document` for pictures (`lib/photos/files.ts:28-33`) and `ScribeFiles` can mark a path excluded and read it back (`modules/scribe-files/index.ts:9-11`; Swift `ScribeFilesModule.swift:26-38`) [V]. **Rec** reuse both: `lib/days/store-file.ts` calls `photosDirectory`'s sibling helper `appSupportDirectory('days')` (a 6-line extraction in `lib/photos/files.ts`, owner `mobile`) and `ScribeFiles.setExcludedFromBackup(uri, true)` then `isExcludedFromBackup(uri)`.
- Not Caches, not Keychain, not `settings`. Protection class no weaker than the database's (NS-47-R6, SEC-R15 [U: not read this run]); **Rec** `NSFileProtectionComplete` is not possible for a file read by a background re-plan, so default `completeUntilFirstUserAuthentication` through the same Expo File default; OQ-D2 for `security-architect` (default: match `scribe.db`, whatever it is).

### 4.2 Format and version (NS-46-R6, NS-47-R28)
`{ v: 1, owner: 'local' | '<ownerKey>', dismissedOn?: 'YYYY-MM-DD', ticked: { '<dayId>': { move?: { date: 'YYYY-MM-DD', always: boolean, year?: number }, authority?: string, offYear?: number[] } }, hemisphere?: 'n' | 's' }`. Ids and overrides only, never a copied date (NS-46-R6). A higher unknown `v` is read for known keys and never rewritten or deleted; a lower `v` is migrated in memory and written once. No iOS-only field (Android reads the same file, FR-LCY-31). `ownerKey` is the first 16 hex of SHA-256 of the signed-in user id (`expo-crypto` is a dependency, `package.json:29` [V]); a phone that never signed in uses `'local'`.

### 4.3 Write rules (NS-47-R6, R28)
- Write order (nothing sensitive is on disk until the exclusion is proven): (1) create an EMPTY `days.v1.json.tmp`; (2) `setExcludedFromBackup` on it and read back `isExcludedFromBackup`; false stops here with the empty temp deleted; (3) only then write the bytes into the temp; (4) rename over the final (a rename keeps the attribute; the read-back runs again on the final); if it reads false the final is truncated to empty and deleted, and the store reports unavailable; (5) the same read-back runs on every open before the first read, so a file that lost the attribute (a restore, a copy) is never used. A launch sweep deletes any `*.tmp` left by a kill (AP-7). If the module is absent (Expo Go, web) or any read-back is false the store refuses to write, returns `{ ok: false, code: 'days_store_unavailable' }` (the one local code, `21:340`), and C-S24 shows its calm line (NS-46-R40). A unit test with a fake `ScribeFiles` returning false asserts 0 bytes written (NS-47-R28).
- Read: absent file is an empty store. A corrupt or unreadable file fails closed: no library note is planned and no crash; the file is never deleted on a failed read (`unknown v` rule). Typed days stay visible (NS-46-R40).
- Atomic and single writer: one in-process queue (a promise chain) serialises writes; a tick is saved as it is made (`21:242`).
- Restored phone: the file is excluded from backup, so it is absent; `culture.asked` lives in `settings` (backed up) and holds no tradition, so the ask does not return (NS-47-R6). The call-out says "Only on this phone" only if the device-to-device transfer row of J-CUL-01 shows the file absent on the second phone; else the words become "on your devices" (`content` and `privacy`, NS-47-R6). **Unverified** until the walk.

### 4.4 The module and its one reader (NS-47-R11)
`apps/mobile/src/lib/days/`: `store-file.ts` (IO), `store.logic.ts` (pure reducer: tick, untick, move, setHemisphere, clearAll, parse, migrate), `index.ts` (the only public surface: `loadDays()`, `tickDay(id)`, `untickDay(id)`, `moveDay(id, move)`, `clearAllDays()`, `subscribeDays(listener)`, `daysForDate(isoDate)`, `plannableDays(now, tz)`), `render.ts` (the lock-screen render of file 14 section 2), `session.ts` (`endDaysSession()`). ## 5. Time zones and DST for a fixed 09:00 (NS-46-R10, R11)

- **Fact** iOS calendar triggers carry no zone and fire at the phone's local wall time (`scheduler.ts:13`, `triggerFor` `:101-113`) [V]; the planner holds `date`, `hour`, `minute` strings plus an epoch for ordering (`planner.ts:113-122`).
- A library day plans as `{ date: 'YYYY-MM-DD', hour: 9, minute: 0 }` after `clampReminderTime(LIBRARY_DAY_TIME, window)` (`planner.ts:177`; the window is 07:00 to 21:30). `LIBRARY_DAY_TIME` is `BIRTHDAY_TIME` (`planner.ts:139`, 09:00) re-exported, so there is one 09:00.
- DST: 09:00 is never inside a spring-forward gap or a fall-back repeat in any zone the app targets [E, gaps sit at 00:00 to 03:00; **Unverified** for every IANA zone, so the test sweeps all zones `Intl.supportedValuesOf('timeZone')` returns, if Hermes has it; else a hand list of 12 zones incl. Lord Howe and Chile]. `zonedToEpoch` (`tz.ts:75`) is used only for ordering and quiet-hour checks, as today.
- Astronomical days: resolved with `localDateOf(instant, planningZone)`; on a zone change (NS-32-R16, `21:242`; the scheduler today re-plans on the store bus and on foreground only, `scheduler.ts:248`, so the foreground handler compares zone and local date with the last plan and forces a re-plan: file 14 section 1.6) every pending astronomical note is re-resolved. A fixed or rule day keeps its calendar date. A flight over the date line moves a floating trigger to the same calendar date in the new zone: at most one note per date still holds (the chooser keys by date).
