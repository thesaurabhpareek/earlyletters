### 3.3 Region hook (File 28, PR #424)
- Fact [V] The hook is `public.hook_before_user_created(event jsonb)`, security definer, `lock_timeout 200ms`, fail open (counts `error`), reads `event->metadata->>ip_address` in memory, maps to a country with `ops.country_of`, and refuses with `{error:{http_code:403,message:'signup_unavailable_region'}}` only for a `scope='country'` row with `status='block'` (migration lines 236-290). Grants go to `supabase_auth_admin` only (lines 283-288). Config is not in `config.toml` ("CLI key not verified"; PR diff) so enabling it is a hosted dashboard step.
- Rec FS-10 Phone mapping: `authErrorKind` (`errors.logic.ts:22`) maps a 403 whose message is `signup_unavailable_region` to a new `AuthErrorKind` `region_refused` (the union is at `machine.logic.ts:30`). It must not join `OUTAGE_ERRORS` (`gate.logic.ts:164`): a refusal is not an outage and Try again would fail identically (NS-40-R14). Compare by message, never show or log it. Test titles in part 4; mutant: add `region_refused` to `OUTAGE_ERRORS`.
- Rec FS-11 Screen: E-S04.refused-region as a `StateScreen` (CL-110, GAP-LOG:621): one PROPOSED line `system.region.title`/`system.region.body`, Terms and Contact us as quiet actions, no Try again, no drawing of a map. Never "sanctions", "blocked", "country".
- Risk RK-1 and **Conflict CF-8** (email path): `signInWithOtp` with `shouldCreateUser: true` fires the hook only for a new address, so from a refused location a new address answers `region_refused` at Send while a known address is sent a code. That tells a person in a refused place whether an address is new, which collides with NS-41-R2 (P0: known and unknown addresses look identical, same words, same request). Whether that is tolerable is not the design's call. Ruling: product with `security-architect`. Default pending the ruling: build NS-41-R2 as written (no change to the send path), keep the per-address 60 s and per-IP limits, and record the signal as a known residual in `ABUSE-AND-FAILURE-CASES.md`. A design that removes it would need the hook to refuse known addresses too, or the phone to show the same screen for both; neither is in any card.
- **Conflict CF-7** (hook fails open; the card proposes fail closed): the migration fails open on any lookup error and counts it (`20261031000000` lines 244-272: `geo_unknown`, `error`, `return '{}'`), but NS-40 section 6, row Outage, says that if the lookup itself fails while Auth is up the hook fails closed (no account made) and the phone shows the outage screen, marked PROPOSED, `security-architect` to confirm. The two cannot both hold. Ruling: product (the card) with `security-architect` and the founder (it is a sanctions control, D-131, against availability of sign-up). Default pending the ruling: build to the card, so the phone treats a hook error as the outage screen, and tell `data-architect` the migration needs a fail-closed branch; until then the founder records in DECISIONS that the hook fails open. Fail closed makes a Geo table fault a sign-up outage for every new person, so it needs an alert (`ops`).
- FS-14 and Risk RK-2 The migration timestamp `20261031000000` is older than develop's newest (`20261109000000` [V]), and APPLY.md calls it File 28 "Pending". A CLI that refuses out-of-order files would reject it. Not mine: `data-architect` re-stamps it (migration task, never written by `sync`); the F4 point in `data-and-sync.md` section 6 still holds (CI never migrates staging or production).
- Unverified: whether the hook fires for Sign in with Apple's `signInWithIdToken` user creation. The card requires it (NS-40-R10, a staging test); Supabase documents the hook as running on any user creation [U, not fetched].

### 3.4 The Swift Declared Age Range module (FS-12)
**Rec shape.** `apps/mobile/modules/age-range/` beside `scribe-photo`: `expo-module.config.json` (`{"platforms":["apple"],"apple":{"modules":["AgeRangeModule"]}}`, the form at `modules/scribe-photo/expo-module.config.json`), `ios/AgeRange.podspec`, `ios/AgeRangeModule.swift` (one file), `index.ts`. JS wrapper `lib/age-range.ts` exports `readAgeSignal(timeoutMs = 3000): Promise<'minor' | 'adult' | 'unknown'>` and nothing else. No value other than that enum leaves the module; no range, no bound, no date.
- Swift: `#available(iOS 26.2, *)` guard (card: iOS 26.2 SDK, `isEligibleForAgeFeatures`); read eligibility; if eligible, request the age range once with a gate at 18; map "sharing under 18" to `minor`, "sharing 18 or over" to `adult`, declined, error, ineligible and not-iOS-26.2 to `unknown`; race a 3 s timeout in JS. API names are from the card and the compliance input 2.2 and are [U]: I could not read Apple's page (fetch returned the title only), so the exact `AgeRangeService` method signature and the framework name `DeclaredAgeRange` must be confirmed on a Mac with Xcode 26.2 by `mobile` before the PR (the PR's first commit is a compile-only skeleton).
- Podspec: the framework is weak-linked because the deployment target stays iOS 17.0 (`app.config.ts:44`); on 17 to 26.1 the call returns `unknown` at once and our question decides (card section 5).
- Entitlement `com.apple.developer.declared-age-range` is added through `ios.entitlements` in `app.config.ts` (the object at `:260-262` already carries the data-protection key) in the same PR, with the App ID capability enabled by the founder in the developer portal (FS-13).
- JS wiring: `AgeGateScreen` (`components/gate/age-gate-screen.tsx`) calls `readAgeSignal` on mount, before the question draws content but never delaying the frame: the question renders at once and a `minor` answer replaces it with the stop and writes only `ageGate.stoppedAt` (R5). An adult answer changes nothing (the question still shows). A timer, a spy test and a scan prove no write carries the value (R6).
**Review risk (state it plainly).**
1. Apple: the entitlement is new to the App ID; an unprepared capability fails the EAS build at signing [E]. The age-assurance Q&A requires Xcode 26.2 or later for the build (compliance input 2.2, [L] primary, read by `regulatory-affairs`); `eas.json` pins no `image` [V: grep], so the default image and Expo SDK 57 with RN 0.86.3 on Xcode 26.2 is Unverified. Spike first: one TestFlight build with the module compiled and the call stubbed.
2. Review notes: App Review 5.1.4 and 2.3.8 wording (card Claims: never "verified adults", "kids"); the Notes name the entitlement and that no age is stored.
3. Label: an entitlement without a declared label effect fails BL-975's guard (`LABEL_GUARD.md`); the PR body carries "Label effect: none, memory only" (card NS-40 section 18).
4.
