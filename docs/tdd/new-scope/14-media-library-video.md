## 1. Facts from the code (what the design stands on)

- **F1.** Develop has no `entry_media`. #835 (`39cf30d3`, open, founder-gated, two PASS WITH NOTES rounds) adds it as migration 11: `kind CHECK (kind = 'photo')`, `ext CHECK (ext = 'jpg')`, `photo_text <= 2240` and `place <= 960` code points (16 per grapheme), `CHECK ((entry_id IS NULL) <> (draft_id IS NULL))`, two partial indexes and `UNIQUE INDEX entry_media_one_photo_idx ON entry_media (COALESCE(entry_id, draft_id))` (`migrations.ts:429-470` at that head).
- **F2.** The store API is one picture per owner: `get(ownerId)` returns one, `put` deletes the owner's rows and inserts one (#840 `entry-media.ts` `get` and `put`). The eraser, Keep move and sweep already loop or update by owner and so are multi-safe (#840 `device.ts:102-109`, `store.ts:512`, `housekeeping.ts:23`).
- **F3.** The Photos lens keeps `ReadonlyMap<entryId, StoredPhoto>`: one picture per letter (#840 `lens.ts`). Find's photo source reads `... FROM entry_media m WHERE m.entry_id = e.id LIMIT 1` (`lib/find/sources.ts:53` on develop): the first row only.
- **F4.** The sweep deletes a row whose file is missing, "so the letter reads whole with no picture and no message" (#840 `housekeeping.ts` header and `missingFileRows`; ADR 0028 D1 "Kill-safety order" step 3).
- **F5.** `scribe-photo` picks one image: `filter = .images`, `selectionLimit = 1` (`ScribePhotoModule.swift:136-137`), re-encodes at 4,096 px and 0.9 (`:50-51`), keeps no `Progress` (`:167`).
- **F6.** `modules/scribe-files` exists on develop with `setExcludedFromBackup(uri, bool)` and `isExcludedFromBackup(uri)` (`index.ts:10-11`), and `lib/packs/app-support.ts` already makes an Application Support folder, excludes it and reads the flag back (`:31-40`). `11-foundations.md:28` and `:230` say `expo-file-system` has no backup-exclusion API and so write the copies natively; they do not mention `ScribeFiles`, which gives JavaScript that call (Conflict C-6).
- **F7.** Export is schema 1.6.0 with `photo: null` (`schema.ts:90, :140`). `pack.ts` holds one whole file in memory at a time and has no ZIP64, limit `MAX_EXPORT_BYTES = 3_900_000_000` (`pack.ts:14, :21`); `DELETION_AND_EXPORT_SPEC.md:322` promises ZIP64 and a split per child-year above 2 GB.
- **F8.** Kill switch keys on develop are `sync, invites, photos, packDownloads, serverContent, backupUploads, escrow, statusReport`; `photos` is documented as "Photo upload and signed photo URLs" (`packages/api/src/kill-switches.ts:10-16`). The flag list is pinned by `test/capabilities.test.ts:242`. ADR 0029 is not on develop.

Free space is read with `Paths.availableDiskSpace` and the privacy manifest already declares the DiskSpace category (`privacy-manifest.ts:109-117`; `lib/capture/free-space.ts:1-12`).
- **F10.** No `expo-video`, `expo-media-library` or `expo-image-picker` in the lockfile (`ALREADY-HAVE.md:19`, #920). Server: no `entry-media` bucket and no signed-URL function exist (`24-engineering-handoff.md:153`); `entries.photo_path` stays null (ADR 0028 D6).

## 2. Data model for NS-52 (Variant A: nothing on a server)

**2.1 `entry_media` after the media migration (the shape; column levels in the migration comment, DATA-REQ-001).**

| Column | Change | Level | Note |
|---|---|---|---|
| `kind` | CHECK `IN ('photo','video')` | L1 | the only list a reader switches on |
| `ext` | CHECK coupled to kind (below) | L1 | `jpg` for photo; `mp4` or `mov` for video |
| `position` | new, `INTEGER NOT NULL DEFAULT 0`, CHECK `>= 0 AND < 1000` | L2 | the parent's order, dense per owner. The card calls it `order`, a reserved word in SQL (Conflict C-2) |
| `duration_ms` | new, nullable, CHECK `> 0 AND <= 600000` | L2 | videos only; the 60 s limit is code (`limits.ts`), the CHECK is a ceiling like 11's text ceilings |
| `bytes`, `sha256`, `width`, `height` | unchanged | L1, L4, L2, L2 | a video's `bytes` is up to 100 MB; `sha256` is computed natively over the stored file (part 2, 1.4) |
| `photo_text`, `place` | unchanged | L4 | the parent's words for one item; for a video too. Rec: the same field is the "Describe this" text of NS-52-R28 (OQ-M3) |

Coupled CHECK (Rec; it sits in the rebuild under the default path B, or in #835 under A-minimal): `CHECK ((kind = 'photo' AND ext = 'jpg') OR (kind = 'video' AND ext IN ('mp4','mov')))`. Two triggers hold the coupling with `duration_ms`, on INSERT and on UPDATE (four triggers, or two with `BEFORE INSERT OR UPDATE` split as SQLite requires): `entry_media_video_needs_duration` and `entry_media_photo_no_duration`, `RAISE(ABORT, 'media_shape')` with a fixed code, no value in the message (TDD 01 4.2 rule 2). Under the rebuild the coupling can be a table CHECK instead, and `ADD COLUMN ... CHECK` across columns is not needed (whether expo-sqlite 57 accepts any `ADD COLUMN ... CHECK` is Unverified). Types: `MediaKind = 'photo' | 'video'` is declared once in `lib/photos/types.ts` and the closed union `MediaErrorCode` (`media_not_available`, `no_space`, `video_unreadable`, `video_too_large`, `video_too_long`, `media_limit`, `media_missing`) once in `lib/photos/media-errors.ts` (CODE-R13, CODE-R15).

**2.2 What replaces the one-picture index (Rec).** Drop `entry_media_one_photo_idx` (`DROP INDEX`, no rebuild; ADR 0028 D1 "One picture per letter is the unique index, not the table shape"). Add `entry_media_owner_pos_idx ON entry_media (COALESCE(entry_id, draft_id), position, added_at, id)`, a plain index: a unique `(owner, position)` would fail the moment a reorder swaps two positions (SQLite checks each row at once). The limits (6 pictures, 2 videos, CL-047) live in one constants file, `lib/photos/limits.ts`, used by the picker's `selectionLimit` and the check (NS-52-R1); they are not in the schema because the numbers are ASSUMED and the founder may change them. The DB has two guards that do not depend on those numbers: the coupling above and `position < 1000`.

**2.3 Order.** `position` is dense, 0 to n-1 per owner, picker order first (`PHPickerConfiguration.selection = .ordered`, Unverified), then later adds at the end. A reorder or a remove rewrites every position of that owner in one transaction. Ties (should one ever appear) break by `added_at`, then `id`. The lens card of a letter shows the item at the lowest position (OQ-M4). The letter page shows all items in order.

**2.4 Files (Rec; names follow the plain-name rule `^[0-9A-Za-z-]{1,64}\.[0-9A-Za-z]{1,8}$` at `lib/photos/files.ts:39`, which allows one dot).**

| What | Where | In iPhone backup | Names |
|---|---|---|---|
| Stored picture | `Library/Application Support/photos/` | yes (ADR 0028 D1; NX-39 F9) | `<id>.jpg` (unchanged) |
| Stored video | `Library/Application Support/media/` | yes, same as pictures (NS-52-R19 line, CR-62 item 4); OQ-M2 | `<id>.mp4` or `<id>.mov` |
| Poster frame, stored | beside the video | yes | `<id>-p.jpg`, 1,280 px long side, no metadata |
| List and page copies | beside their source (NS-37) | no (flag set, read back) | `<id>-512.jpg`, `<id>-1280.jpg`; posters `<id>-p512.jpg` |
| Temporary pick copy | `Caches/ImagePicker/` (existing) | n/a | plain name made by JavaScript |
| Transcode output before the move | `Caches/ScribeMedia/` (new, swept at launch) | n/a | `<id>.mp4` |

A row stores no path (Rec): `poster_path` in the card (`27:408`) is dropped in favour of a name derived from the media id. Reason: the sweep already rebases paths after an app update because the container path changes (`capture/sweep.ts:8`), so a stored absolute path rots (Conflict C-2). The poster of a video is the frame at t = 0, chosen by a rule, never by judging the picture (NS-52-R29; R27 is the parent's own choice for print, later).

**2.5 Classification.** Every new column carries its level in the migration comment (`local-classification.test.ts`, `11-foundations.md` section 6 rule 5). The video file, its poster, the derived copies, `sha256` and the typed words are L4. `position` and `duration_ms` are L2: neither identifies a child or a family alone. A hash of a picture is L4 (`DATA_CLASSIFICATION.md` 1.1.2, ADR 0028 D1). `privacy` rules the class; this file proposes (OQ-P1).

## 3. The moments index (NS-51-R6, R23; the Conflict line)

**Conflict C-1 (to product; found by delta 3 section 5 item 1 and confirmed at `27:139` and `:156`).** R6 says the index is "in the phone database, registered for Erase, excluded from the iPhone backup". R23 says it is "absent (excluded from backup, read back)". `scribe.db` is one file in the backup (Assumption: the file is backed up whole), so a table in it is in the backup and R23 cannot hold. Section 11 says "Phone database" and "not in backup" in one row (`27:210`). Handoff 24 resolves it with a second SQLite file (`24:119`).

**Rec (a third way).** The index is at most 30 moments of at most 6 identifiers (R6): about 180 identifiers, under 10 KB [E: about 40 bytes each]. No query runs over it that a loop cannot. So: one versioned JSON file, `Library/Application Support/moments/moments.json`, in a folder created and excluded by the existing helper (`lib/packs/app-support.ts:31-40`, name union extended to `'moments'`) with read-back at every open; if the flag reads false, nothing is written (fail closed) and the feature shows its off state. Why not a SQLite file: WAL files (`-wal`, `-shm`) are separate files created later, so a flag on the main file leaves them in the backup, and a second migration chain would need its own upgrade tests for 10 KB. Cost: a hand-rolled schema check and atomic write (temp file, rename in the same folder). Its schema is a typed constant `moments.schema.ts`: `{ v, owner, optIn, paused, albums[], builtAt, moments[{ start, end, ids[] }] }`, each field labelled L2, L3 or L4 in the constant; a test fails on an unlabelled key (the phone classification rule; DATA-REQ-002).

- **Per account (R24).** `owner` holds the account scope (BL-961's `scopeOf`, `11-foundations.md` 6.1). A file whose owner is not the current scope is deleted on open, not read. Sign-out, Erase everything, Delete account and a system-ended session delete the folder (R17); the folder joins `eraseDeviceFiles` by name (`erase-everything.ts:57`) and is listed in the Erase test.
- **Restore (R23).** The folder is not in the backup, so a restored phone has none, the opt-in reads off and no ask returns by itself. Apple's own permission state after a restore is Unverified (the card says so); our file is the only thing the feature trusts.
- **Pause (Q-PM-12, CL-057).** Writes `paused: true` and empties `moments` and `albums` in one rename. Turn off deletes the file.
- **Not a migration** (ADR 0028 D4 pattern, `architecture.md` AB-7): derived data, rebuilt from the library. AB-7 says derived data is rebuilt "from `entries` and `entry_media`"; the moment index is rebuilt from the library, which is Amendment A-7.
- **Rule in `packages/core`.** The moment rule (R7) is a pure function with an injected clock and zone (FR-AIS-58, `functions/ai-and-speech.md:343` per delta 3). It takes `{ id, createdMs }[]` and the marked-day dates; it returns at most 30 moments. The open draft #754 `moments.ts` takes a `cityKey` and is not a base (`24:120`).

## 4. Migration plan: 11 versus 12

The question (handoff 24 Q-E12, `24:129` and `:275`; product's note on #835 of 20 Nov 17:16; card 27 says "local migration 12"): amend #835 before it merges, or add a later migration. Both are laid out. Facts both rest on: migration 11 has shipped nowhere (no `ios-v*` tag, no release branch; Review A at `39cf30d3` on #835). SQLite cannot alter a CHECK, so changing `kind` or `ext` after 11 is a table rebuild (copy to a new table, drop, rename; Assumption: SQLite 3.x documented behaviour). One view does read it: `searchable_letters` embeds a subquery on `entry_media` (`find/sources.ts:50-53, :87`), so a rebuild must `DROP VIEW` first (SQLite refuses to rename a table while a view names a table that is gone; Assumption) and `ensureSearchView` makes the view again at the next launch (`sources.ts:100-110`, a view holds no data). No foreign key points at the table. `migrate()` runs each step in one transaction with `user_version` set inside it (`migrations.ts` `migrate`), so a rebuild is atomic and short at 1,000 rows [E: milliseconds].

| | A. Amend 11 in full (handoff 24) | A-minimal. Amend 11's two CHECKs only (Rec to Karma and product) | B. A later migration (card 27; DEFAULT) |
|---|---|---|---|
| What changes in #835 | `kind`, `ext`, drop the unique index, add `position`, `duration_ms` | the coupled CHECK of section 2.1 only; keeps the unique index | nothing |
| Rebuild on a real phone | never | never | once, for any phone that took 11, with the Find view dropped and made again |
| Build 13 invariant "one picture" | enforced by code only (index gone); mutant A15 (unique index) dies | still enforced by the index; mutant A15 stays killed | unchanged |
| Cost to #835 | re-review of schema, tests, ADR 0028 D1; adds columns no Build 13 code writes | about 4 lines, one test row (CHECK refuses `video`+`jpg`), ADR 0028 D1 amendment; one more review round of a merge-ready, founder-gated PR | none |
| Risk | ships an unproven shape (poster, duration) before the spike; wrong guess means a rebuild anyway | a wrong `ext` list means a rebuild anyway; the list is `jpg`, `mp4`, `mov`, which covers an `AVAssetExportSession` mp4 or mov output | none to #835; one rebuild test, on the seeded book |
| Product text | contradicts card 27, which means a later migration for `kind` | contradicts card 27 in behaviour: the card puts the `kind` change in a later migration and #835 unchanged (Conflict C-4) | is what card 27 says; only the number differs |

**Default: B; Rec to Karma and product: A-minimal.** Card 27 and Karma's ruling make B the build path: #835 merges unchanged. A-minimal is the cheapest way to remove the one expensive step (the rebuild), leaving ADD COLUMN, DROP INDEX and CREATE TRIGGER, but it re-opens #835 to #839 and goes against the card, so it needs a ruling (product, #913 blocker 4), not a statement. PR 1, ADR amendments A-1 and A-8 and part 3 are conditional on that ruling. Under B the cost is one rebuild with the proof of section 4.2. #835 is founder-gated either way; this file asks nothing of the founder except that A-minimal would add one review round.

**4.1 L-numbers.** `data-and-sync.md:39-45`: L11 `entry_media`; L12 Firsts (wave 4); L13 seals; L14 `author_signs_as`; L15 withheld words; "L13 to L15 take numbers in merge order". The media migration is drop C, after wave 5, so it is **L16 by today's order** and takes the next free number at merge. Card 27's "12" is wrong as a number under every option. It is one migration for NS-52. NS-51 has none (JSON file).

**4.2 Upgrade test (AP-3; `architecture.md:125`).** `migrations.v16.test.ts` in the `migrations.v9.test.ts` shape and a line in `migrations.test.ts:247`. Seed with `scripts/qa/asha-book/plan.mjs` at the `book` size (1,000 letters, 300 pictures; `MEASUREMENT-PLAN.md:43, :62`); run 11 to 16 on a `node:sqlite` copy. Asserts: every `entries`, `drafts`, agreements and `entry_media` row byte-identical except the two new columns (`position` 0, `duration_ms` null); `sync_outbox` unchanged; two rows for one owner now insert; a video without `duration_ms` is refused by its trigger; a photo with `ext = 'mp4'` is refused by the CHECK; `PRAGMA integrity_check` is `ok`; re-running `up()` is a no-op (the survivor M13 of Review A).
