### 9.4 FS-34 Step-up for deleting the account (R5, R6, R7, R15; O-17)
- Fact [V] Today deletion needs: a signed-in session, the typed word `delete` (`logic.ts:61-70`), a connection (R15: `deletion.offline`), at most 5 requests a day, and works without agreeing to a new Terms (`request_account_deletion` checks `require_user()` only). No re-authentication: the template "Your code to confirm account deletion" exists (`config.toml:106-108`) and no app code calls Supabase reauthenticate (input G5).
- Card default (O-17): no sign-in step-up; the 30-day undo and the two emails are the guard (Apple wants deletion easy, 5.1.1(v)). Function FR-SEC-06 (`risk-security.md:108`, P1): a phone owner check (Face ID, Touch ID or passcode) before Erase everything, "not a sign-in, so it does not add the friction G5 warns about". FR-SEC-12 adopts G5 and G6 emails.
- Rec: build exactly the default: typed word, scheduled date, both emails, cancel anywhere (R9 `[NS-45-R9]`, the scheduled screen returns at sign-in). Add one shared `lib/security/owner-check.ts` `ownerCheck(): Promise<'passed' | 'cancelled' | 'unavailable'>` over `expo-local-authentication` (`authenticateAsync`; `app-lock/controller.ts:106` is the only caller today; the package is a baseline-failing import in the sandbox, so tests stub it), used by Erase everything per FR-SEC-06 (`FP-16b`). Delete account calls it only if product rules OQ-F4 yes (my recommendation, facts below); until ruled the card's default is the build. A server-side step-up (`reauth_required`, SQLSTATE `SCSTP`, `envelope.ts:72`) is reserved for backup and recovery steps (card; `first-run-auth-security.md:90`) and is not extended.
- Step-up facts the decision needs [V: `20261005000000:408-455`]: the request acts at once on the server, not at day 30. It soft-deletes the author's entries (`deleted_at`, reason `account_deletion`) and the books where the person is the only parent, so their words vanish from every signed-in phone at the next pull until a cancel restores them; the confirmation email can arrive up to 15 minutes after the request (worker cron, `worker.ts:4-11`), so it is not a real-time alert. These two facts weigh against "no guard" more than the card's O-17 text says: someone with an unlocked phone can hide a family's letters and the owner learns by email up to a quarter hour later (cancel is one tap, 30 days). That is why OQ-F4's default is now: add `ownerCheck()` before the request as well, as a phone-side check, not a sign-in. `ownerCheck()` must call `authenticateAsync` with `disableDeviceFallback: false` (as `app-lock/controller.ts:106` does) so a passcode works when Face ID is unavailable, and return `unavailable` (proceed on the typed word alone) on a phone with no passcode, per FR-SEC-06. This is a recommendation for product; the card's default (no step-up) remains the build until ruled.
- Typed word wrong (card section 5): the button waits with a reason in words (PROPOSED `deletion.typeDelete` reason), announced.
- Step 1 words (R5): add pictures (phone only; "v1.0 makes no photos" becomes false with NS-01), the sealed-letter line (D6, with NS-06 B), Export first, Plus not cancelled. PROPOSED keys; founder approves; counsel reads (legal-adjacent).
