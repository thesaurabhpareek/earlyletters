### Notes (most serious first)
N1. Let it go leaves the draft's picture until the next launch (ADR D5). ADR D5 says "Let it go on a draft does the same for draft_id rows". Here only the launch sweep removes a let-go draft's file and row (housekeeping.ts:40-49). letItGo (listen.tsx, review.tsx) never calls erasePictureOf, and no slice through #840 wires it (grep). No draft can hold a picture in this slice, so this does not block 3a. It must be closed before the slice where a draft gets a picture (4a or 4b), or the child's picture and the parent's photo_text stay on the phone after Let it go until a cold launch. The test title at photos-phone.test.ts:99 ("a let-go draft the same") overstates: the test calls erasePictureOf('d1') directly, not the let-go path.

N2. The inventory for the new store is missing (DQ-R02, DATA-REQ-001). migrations.ts:14 says "New columns need a row in docs/legal/DATA_CLASSIFICATION.md 4.5", and ADR D1 says the photos PR adds the data-policy.md 4.4 row. This PR adds neither, no slice through #840 does, and I found no handoff to privacy. Migration 11 ships unconditionally, so every phone gets this store. DQ-R02 and DQ-R03 are "not yet" (WS-19), so no check fails. Please open a handoff to privacy. Levels for privacy to rule on, not decided here: id, entry_id and draft_id are L2, while 4.5 has entries.id and drafts.id at L3; bytes is L1 against audio_bytes at L2; kind and ext are L1 against enums at L2.

N3. Three claims are proven only by source scans that survive a mutation. (a) Keep inside the transaction: photos-device.test.ts:715 passes with the move after the transaction (M15). (b) The eraser call: photos-phone.test.ts:127-131 passes with the call commented out (M14). (c) Erase everything deletes the folder: photos-device.test.ts:278 passes with the delete removed (M16). ADR 0028's test list names behavioural tests: "a letter erased on another phone of this author loses its picture here", and Erase everything "against the real adapter". My scratch tests show the behaviour is right today. Recommended: replace the three scans with behavioural tests over erase-all.test.ts's mocks (real eraseAudioFile, real eraseEverything, an injected failure on the Keep move).

N4. put() quietly treats any unknown owner as a draft (DQ-R07). entry-media.ts:50-55 stores any id that is not an entries row as draft_id, even when no drafts row exists. The next launch sweep then erases that file and row without a word (housekeeping.ts:40-49), taking the parent's photo_text and place with them. A caller bug, such as a stale screen on a just-purged letter or a picture put before its draft row exists, fails silently at the next launch instead of at put. Suggested: put() throws a typed error when the owner is neither an entries row nor a drafts row.

N5. The sweep drops a row on the strength of a listing alone (housekeeping.ts:51-53). Dropping the row loses the parent's photo_text and place (L4). On iOS a failed listing throws (handled) and a missing folder lists as [] (files.ts:95), which is correct. On Android, expo-file-system lists an unreadable folder as empty (the stand-in's `listsAsEmpty`), and every row would go. Before Android, check the file exists before dropping a missing-file row, or skip that pass when the listing is empty but rows exist. The sweep is also safe against a concurrent pick only because writers put the row in the same tick as the file write (3b's session.ts:129-130 does). A comment in housekeeping.ts would keep it that way.

N6. Downgrade and the way back.
- Ruling reason 2 does not match today's code. The reason says gating the migration list "would stop a phone at launch, with a newer-file error", but a newer file keeps the app running (launch.logic.ts:12-17; MOB-09 is not built). The other reasons carry the ruling.
- A phone that ran a photos-on build and then an older v10 build: that build's Erase now and Erase everything remove rows (removeEverything reads the schema) but leave the files in Application Support/photos, which are also in the iPhone backup, until a v11+ build's sweep. This is inherent. A line in the TestFlight notes would help.
- The way back as worded ("a later migration drops the empty table") is SQL only. On any phone that ever ran with the switch on, it would leave pictures in photos/ with nothing left to sweep them. The drop needs a folder removal at launch alongside it.

That is not so. sweep.ts imports ./erase, which now imports ../photos/device statically (erase.ts:26). Only the kill harness avoids it, by mocking ./erase (qa-kill-harness.test.ts:132). sweep.disk.test.ts loads it and fires the photo sweep without awaiting it. Harmless today. Fix the comment or the import.
