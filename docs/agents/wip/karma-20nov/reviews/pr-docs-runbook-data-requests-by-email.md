## What and why

BL-779 (CR-60, CLO risk 1: "promises he keeps by hand, with no tool or runbook"). The 0.9.0 Terms and Privacy Policy say the founder will, by hand: delete an account (Terms 10.1, Privacy 7), withdraw the agreement to sync (Privacy 9), see, export, correct or delete (Privacy 10), close an under-18 account (Terms 2.1, Privacy 8) and delete TestFlight feedback (Privacy 7). Only the under-18 route and a stuck deletion had a runbook.

New `docs/ops/runbooks/data-requests-by-email.md`, linked from the index in `docs/ops/README.md`. Documentation only: no code, no migration, no `docs/legal` change, no new promise. It opens with a table of what each 0.9.0 sentence promises and the time it names. For every route it gives: who may ask, how the founder confirms control of the account email before any change (DSR-R02), the steps and tools that exist today, what is not built, the time in the text, and how to record the request without keeping content. It ends with a section listing every promise that cannot be kept by hand today, a list of what is unverified, a one-line rehearsal checklist ("run each route once on a fictional account before the pages go live") and the Shown, Records, Never and Decline lines.

Things the runbook says that a reviewer should check:
- **Route 1, delete an account by email, is marked CLOSED.** `ops_open_account_deletion` (BL-551) is in no migration; `request_account_deletion` works only for the signed-in person and never accepts `support` as a source. The Delete account row is hidden in the alpha builds unless an EAS environment variable (not in the repo) switches it on. With the tool unbuilt, "we will do it by hand" in Terms 10.1 and Privacy 7 cannot be kept. The Route 1 reply is neutral (it says "We cannot start a deletion by email yet" and nothing about an account) so it can go to a sender who has not been checked.
- **Other promises that cannot be kept by hand today** are in one table at the top of section 9, for the founder's CR-60 decision: Privacy 9's "we offer to delete what was synced" (once a phone has signed in the app offers no Delete this book, `localDeletionAllowed()` in `store.ts`), the under-18 deletion step, export for a person with no phone (DATA-REQ-054), email-list removal (no steps written) and the Privacy 10 attorney-general step after a refused appeal.
- **Withdraw sync uses a SQL Editor insert as `postgres`.** Chapter 08 names `record_policy_act` with `support_assisted`, but that function refuses the method and the service role has had no insert on `policy_acceptances` since `20261023010000_s02_purge_and_consent_guards.sql` (line 88; `supabase/tests/consent_service_role.test.mjs`). The route follows `supabase/APPLY.md` step 8, item 3. Chapter 08 is out of date on this point; I did not edit it.
- **The control check is an interim method of mine:** a random single-use code with a 7-day expiry, sent as a new message from hello@ to the account address only, at most one per account per 7 days. The message names the request. The person types the code and the word yes; a quoted copy, a "no" or "not me" passes nothing and ends the request, and a changed request needs a new code. The repo has the rule (DSR-R02) and the sentence "a code to the email on your account", but no tool or wording, and does not say how the founder sends mail as hello@ (UNVERIFIED). `privacy` is asked to confirm it at the first rehearsal.
- **Correcting the account name is by hand,** because the name is saved once at sign-in and nothing in the app shows it (its only reader is the export). The runbook reads the person back with the email beside the id, stops unless that is the verified address, then runs one block that checks the id and the verified email together, writes the audit row, and updates the name, raising (and changing nothing) unless exactly one row changed. The id appears once. The block on the page has three tag placeholders (`$<tag1>$` and so on) that the founder fills with fresh `openssl rand -hex 4` values; unfilled, it is a syntax error, so a statement copied from the page cannot run. It also refuses a dollar sign in the name. The sign-in email is never changed by hand (`double_confirm_changes`).
- **The request log has no person id** (chapter 08's field list has one), and it has kinds for safety, legal process and other, an outcome `referred`, and a `legal_date` field: a file cannot null the id at deletion, and `ops.audit_log` already links the ticket to the profile for 12 months. The log lives in a file on the founder's computer, in a folder that does not sync to a cloud drive.
- **TestFlight feedback:** Apple's Help page "View tester feedback" was fetched on 9 Nov 2026 through a tool that returned quotations; the runbook quotes it and keeps the screens themselves UNVERIFIED. It matches `docs/legal/TESTFLIGHT_TESTERS.md` A5 and A8 (16 Oct 2026). Anonymous feedback (no tester email) is not deleted by email. The tester check is adapted (the code goes to the tester email App Store Connect shows), because a tester has no account with us.
- **PROPOSED WORDING** (the founder approves any text a person reads): the Route 1 reply and the code email in section 2. The runbook lists the other macros that do not exist yet (first reply, refusal with the appeal line) and writes none of them. None of the four Erase lines is used.
