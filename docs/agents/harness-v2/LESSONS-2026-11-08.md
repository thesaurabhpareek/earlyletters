## 1. Reviews at heads that then moved
- Wasted: reviews started or posted against a head that changed before the verdict was read.
- Evidence: #517 got 9 head changes on 8 Nov (force-push 08:38Z, then commits 08:42, 08:53, 09:21, 09:23, 09:28, 09:37, 11:40, 17:16 UTC; final head 968328a2, merged). The brief said 3 moves in 2 hours: the log shows 8 in 3 hours, so it was worse. Commit times are author times, not push times (U for exact push times). #532 had commits at 08:41Z and 08:42Z (head 10c7f7cc). #508 had a force-push at 08:41Z and commits at 09:03 and 09:04 (head 51834996).
- Rule: a reviewer first reads the head sha. A review starts only when CI is settled and the head has been quiet 10 minutes. An author session does not push to a PR that holds a review claim. A review binds to the full 40-char sha (CR-44, PR #555).
- Enforced by: the merge-queue script (STALE-REVIEW, WAIT-QUIET); until then the reviewer by hand.
- Covered by: new HV2-B32. Related: HV2-B06 (strict-sha gate core, #559).

## 5. Hand-scanning cost

- Evidence: 139 PRs open on 9 Nov (REST search), each needing head, CI, review and mergeable state.
- Rule: one script answers it, read-only, one table out.
- Enforced by: the script's own tests.

## 6. Repeated permission-gate denials
- Wasted: agents retried a denied action, or asked one PR at a time.
- Rule: after one denial an agent stops. It batches the ask to the founder with PR number, full sha, CI state and a recommendation filled in, and does not retry. The founder naming the PR and the full sha is the unit of consent.
- Limit, said plainly: this is a limit of the setup. An agent cannot grant itself consent and no agent message counts as the founder's. The cost is founder minutes per merge; the harness can shrink the ask, not remove it.
- Enforced by: each agent; the review-prep helper prints the ready-to-paste ask (B36).
- Covered by: new HV2-B36.

## 7. Token waste patterns (from agents' own reports)
- Re-installing node_modules in every review. No per-session cache note exists in the repo (U for the wider setup). Until one exists: one install per worktree, remove it when done (Batch 3 brief). When a script is enough, use `node --test` and skip `npm ci`.
- Reading whole transcripts, re-reading unchanged docs, re-dispatching a lane that already reported.
- Rule: a brief names the exact files and the question. An agent returns the verdict first, then evidence. No agent is re-dispatched without reading its last report. Run `ListAgents` before spawning.
- Enforced by: whoever writes the brief; the coordinator.
- Covered by: new HV2-B36 (review-prep helper) and the rule above.

## 8. CI policy: which checks block a merge
- Wasted: waiting hours on checks that never blocked anything.
- Evidence: branch protection on develop (read via `gh api repos/thesaurabhpareek/earlyletters/branches/develop/protection` on 9 Nov): required contexts are `applied migrations unchanged`, `required`, `compliance-fence`. Strict (up to date) is false. Approving reviews required: 0. Admins enforced: true. Linear history: not required.
- Watch items, not required: `.github/workflows/ios-compile.yml` runs the build job on `macos-26` (line 60); on 9 Nov its latest runs ranged from success to cancelled to in progress. Store-profile launch: no matching workflow found by name, U. The `claude` jobs are skipped on develop head.
- Example: #623 (web PR, head 74771226) changes a package-lock.json and its check "iOS simulator build (no signing)" concluded failure on 8 Nov. The linker error and exit 65 are from the coordinator's report; the cause is unverified (I confirmed only the failed check and the lockfile in the file list).
- Rule: branch protection requires three contexts and a merge waits for nothing else. A red or failing macOS job is NOT ignorable when the PR touches apps/mobile native paths (ios/, modules, app.config, eas.json) or the root package-lock.json, because the iOS build uses that lockfile. For those PRs the reviewer reads the failure and writes one line saying why it is unrelated, or the PR waits. For all other PRs macOS jobs are watch items.
- Strict (up to date) is false, so a green check on an old base does not prove the merged result is green. After any develop-only merge into a PR branch, the CR-52 re-review rules apply (CR-52 cited by the coordinator; I did not find it as a heading on develop, U).
- Enforced by: GitHub branch protection (the three); the merge-queue script lists the rest as WATCH.
- Covered by: new HV2-B37 (put the list in COORDINATION.md).
