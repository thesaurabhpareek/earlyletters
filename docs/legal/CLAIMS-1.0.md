# Claims registry for the 1.0 build (PROPOSED)

Status: **PROPOSED**. Written by `compliance-engineer` on 23 Nov 2026 for BL-867 under exec ruling 6. It is not counsel-approved and says nothing a lawyer has cleared. Under D-168 and D-172 the exec team (CLO, CCO, Chief Privacy Officer; Claude roles, not licensed lawyers, and not legal advice) must confirm it before it is treated as settled; Karma merges after that review. Every "backed" below is an engineering reading of code and tests, not a legal conclusion.

## How this file relates to `docs/legal/CLAIMS.md`

`docs/legal/CLAIMS.md` does not exist on `develop`. Open PR #37 (a 3 Oct privacy data map, a checker and a 26-row privacy and trust claims register) adds a file of that name. That file is the separate **privacy-claims register**. This file does not replace it, edit it or depend on it. This file covers every promise the 1.0 store build makes on three surfaces: the App Store listing, earlyletters.com and the in-app lines. Reconciling the two registers (one file, or two with one index) is a **follow-up row** for `legal` and `compliance-engineer`; it waits until #37 is resolved. Until then PRIV-R17 and LEGAL-REQ-044 point at `CLAIMS.md`, and this file is the working registry for the 1.0 surfaces.

## What the build is (read from `apps/mobile/eas.json`, `build.production.env`)

Servers on (`EXPO_PUBLIC_SERVER_FEATURES` on), recording backup off, status report off, analytics off, account deletion on, English only (`EXPO_PUBLIC_ENGLISH_ONLY` on, `EXPO_PUBLIC_SPOKEN_LANGUAGES` `en`). There is no `EXPO_PUBLIC_PHOTOS` key, so the photo switch (`apps/mobile/src/lib/photos/flag.ts`, `parsePhotosFlag`) is off. The store build hides the "I was invited" door, so there is no co-parent flow (`packages/content/test/claims-capabilities.test.ts`, `storeCoParentFlow`). This matches D-157, D-160, D-170 and, for photos, D-169 (library read off unless the five photo gates close by Fri 27 Nov 2026).

## How to read the table

- **Source**: the file and key the words live in. Words are quoted short; the file is the truth. A per-line text hash (BL-867 asks for one) is **not yet** computed: it needs a script, and agents may not add one in this PR. Follow-up row.
- **Backing**: the code or test that makes the line true. A test is listed only if I opened its file. "(assertion not read)" means I confirmed the file exists and its header names the topic, not that it asserts this exact line.
- **Status**: `backed` (code and a test I read both support the line), `partly backed` (one half is proven, the other is marked), `no automated proof` (true by design or policy, nothing in CI would catch a change), `false today, listed` (the claims test knows it is false in this build and names the row that removes it), `held` (deliberately kept out of the build), `flag` (I found a problem; see section 5).
- **Owner**: the agent handle that fixes the line or its proof (`agents/roster.json`). Owners are proposals.
- Counsel column: every row is **not counsel-approved**. No row records a counsel version, because none exists (D-172: the exec team is the counsel). Exec-team confirmation is tracked in `docs/ops/proposed/bl-841-exec-team-checklist.md`.

## 5. Findings from compiling this file

Each is a gap or a stale line, found by reading. None is fixed in this PR (this file changes no product or legal text).

- **F-01 (S-18).** `reviewNotes` in `packages/content/src/store.en.ts` says there is no account and no server copy. A servers-on build sends different notes (the file's own comment), but the stale field is still in the file. `ops` should confirm which notes the production upload sends, and `content` should remove or update the field. Not verified: the refusal test for `NO_SIGN_IN`.
- **F-02 (S-06).** "Without an account, your book stays on your phone" is a conditional the store build cannot reach, next to a required sign-in. The exec team should decide whether to keep it. Any change is `content` and `legal`.
- **F-03 (S-19).** The Helpful Details draft in `docs/store/app-store-connect-1.0.md` section 10 says the only network requests are signed settings, the model download and StoreKit. That is false with servers on. Owner of that file should correct the draft before it is typed into App Store Connect.
- **F-04 (W-11).** The live Privacy Policy page covers the website only, per `docs/store/app-store-connect-1.0.md` section 4 (BLOCKED). The in-app and store claims about the app rest on a policy that is not yet published. A physical publish step for the founder queue, not an agent action.
- **F-05 (A-06, A-07).** `en.trust.signIn` and `en.trust.settings` are not in `IN_APP_PROMISES` in `packages/content/test/claims-capabilities.test.ts`, although sign-in is on in production and the Settings promise is a screen families can open (screen not opened here). Adding them is a test change for `content` and `compliance-engineer`; it may expose new false claims, so it should land with its fixes.
- **F-06.** PRIV-R17 (`docs/engineering/07-privacy-engineering.md` line 97) names `docs/legal/CLAIMS.md` and says `Enforced by: not yet: PPRIV-04`. LEGAL-REQ-044 (`docs/legal/ENGINEERING_REQUIREMENTS.md` line 364) says the registry gates public claims and names `docs/legal/claims-registry.yaml`, a third name. This file is not machine-read, so nothing gates a claim yet. Making a content test fail a claim string that is missing from a registry is the real enforcement, and remains `not yet`.
- **F-07.** The photo and counsel rows depend on the exec-team review that stands in for counsel (D-172). They are `held`, not approved.
